# SDK UNET-GAME

SDK — исходные модули sjasmplus, которые игра включает в свою программу
вместе с `UNETGAME.INC`. Они загружают DLL, вызывают её экспорты напрямую,
допускают входы по фиксированным квотам (ТЗ §5.1), ведут `now_ms` и
выполняют порядок входа и выхода ТЗ §7. Ядро DLL не знает о SDK: всё, что
касается DSS, прерываний, CTC и квот, лежит здесь.

| Файл | Содержимое |
|---|---|
| `sdk/loader/ugload.asm` | `UG_LOAD`, `UG_FREE`: загрузка через libman, страница и база DLL, сверка с самой библиотекой |
| `sdk/loader/ugenv.asm` | `UG_NETENV`, `UG_NETFIX`, `UG_NETNAME`, `UG_NETVAR`: поля карты INIT_CONFIG и имя DLL по окружению DSS (только DSS `#46`) |
| `sdk/loader/ugnet.asm` | `UG_NETUP`, `UG_NETAUTO`: один вызов от окружения до загруженной и сконфигурированной DLL |
| `sdk/gateway/ugate.inc` | Раскладка блока шлюза, профиль приложения, коды, стоимости обвязки |
| `sdk/gateway/ugate.asm` | Прямые вызовы, `UG_INIT_ENV`, допуск STEP, входы из ISR, такт периода, выход |
| `sdk/time/ugtime.asm` | Адаптеры времени `FIXED_SCHEDULE` и `APP_COUNTER` |
| `sdk/example/netdemo.asm` | Пример смешанного обслуживания (ТЗ §7) и программа стенда M |
| `third_party/libman` | git-сабмодуль libman (загрузчик DLL DSS), подключается через `LIBMAN_DIR` |

Перед `INCLUDE "gateway/ugate.inc"` игра задаёт `UG_BLOCK EQU <адрес>` —
блок шлюза (192 байта, выровнен на 256, постоянно видимая RAM ниже `#C000`;
первый байт — общий замок ISA) и `DEFINE UG_DLL_WIN 1` (окно, для которого
релоцирована DLL; 1 или 2). Пути включения: `-I sdk -I include -I <LIBMAN_DIR>`.

## Порядок работы игры

1. **До игры**, пока работает IM1 и DSS:
   `UG_GW_INIT` (A = текущий `#1FFD`, E = текущий `#9FBD`) →
   `UG_LOAD` (имя файла; libman вызывает INIT) → игра обнуляет регион
   контекста → `UG_INIT_ENV` (IX = блок INIT_CONFIG, HL = профиль).
   Вместо `UG_LOAD` и `UG_INIT_ENV` можно одним вызовом `UG_NETAUTO`
   (A = протокол, IX = блок, HL = профиль): карту и DLL SDK выберет по
   окружению DSS (раздел «Автозагрузка по окружению DSS»). Обнулять
   контекст не нужно: INIT_CONFIG очищает его сам (`CFG_COMMIT`).
2. **Прерывания.** Игра ставит свою таблицу IM2, программирует свой таймер
   (в примере CTC1: `#A7`, константа 164 → 1999,238 мкс при 21 МГц),
   вызывает `UGT_INIT` (HL:DE = начальное `now_ms`), затем `UG_START` и `EI`.
   После `IM 2` вызовы DSS запрещены (обслуживание DSS IM1 остановлено, как
   в Worms).
3. **Обработчик таймера** (IFF = 0): `UG_TICK` → `UG_ISR_NET` с
   `UNETG_SRC_TIMER` → `UGT_TICK` → `EI` / `RETI`. Другие обработчики:
   кадр — `UG_ISR_FRAME`, клавиатура — `UG_ISR_KEY`, звук — `UG_ISR_CBL`
   (только флаг), IRQ карты — `UG_ISR_NET` с `UNETG_SRC_CARD_IRQ`. Каждый
   обработчик сначала обслуживает своё устройство.
4. **Основной цикл:** `UG_STEP` (допуск из квоты main), события
   (`NEXT_EVENT`), RX/TX — всё через `UG_CALL`. Во время паузы игры цикл
   продолжает `UG_STEP` и события: часы, периоды, опрос и TCP идут дальше.
5. **Выход:** `UG_SHUTDOWN` (DE = предел в мс) до OK → игра останавливает
   свой таймер, восстанавливает I и `IM 1` → `UG_EXIT` (A = байт замка,
   ожидается 0) → `EI` → `UG_FREE` (FINI через libman) → возврат в DSS.

## Загрузчик

`UG_LOAD` вызывает `LIBMAN.l_load` для окна `UG_DLL_WIN`. Из записи
`LIBMAN.lib_table` берутся id блока DSS и база. Физическую страницу даёт
`IN` порта окна после `SetWin1/2` (DSS `#39`/`#3A`); затем окно
возвращается к прежней странице. Две сверки (ТЗ §8): `GET_INFO.image_base`
совпадает с базой libman, 32 байта `l_info` совпадают с заголовком L1 по
этой базе. Несовпадение — `UG_LD_BASE` / `UG_LD_HEADER` и `l_free`; отказ
libman — `UG_LD_LIBMAN` (B = `LIBMAN.l_reason`). Раскладка `lib_table` —
внутренняя: `ASSERT LIBMAN.VERSION == 0x0104`.

Программа, разместившая DLL сама (стенд Z), вызывает `UG_ATTACH`
(A = страница, H = старший байт базы).

## Автозагрузка по окружению DSS

Игре не нужно знать, какая сетевая карта стоит в машине. Системные
средства подъёма сети (NETUP для SprinterESP, NETCFG / IFUP для
RTL8019AS, средства 3C509B) уже нашли карту, получили адрес и подключили
модуль к Wi-Fi. Свой результат они оставили в переменных окружения DSS.
SDK читает эти переменные, заполняет поля карты в блоке INIT_CONFIG,
выбирает DLL, загружает её через libman и вызывает INIT_CONFIG. Игра
сообщает только протокол.

Шины ISA загрузчик не касается. Если средства подъёма не запускались,
сети всё равно нет: у Ethernet нет адреса, модуль ESP не в сети. Ответ в
этом случае — `UGN_E_NONET` или `UGN_E_ENV`. Отсутствующую карту при
заданных переменных ядро обнаружит само при подъёме (`hw_state`). GLOOP
загрузчик не выбирает никогда: эта DLL только для стендов Z и M.

### Переменные

| Переменная | Значение | Поле INIT_CONFIG |
|---|---|---|
| `NET` | `WIFI` или `ESP`, `RTL`, `509B` (регистр любой) | `hw_profile` |
| `NET_ESP_HW`, `NET_RTL_HW`, `NET_HW` (3C509B) | `S/#HHH`: слот 0 или 1, база в hex | `isa_slot`, `io_base` |
| `NET_IDPORT` (3C509B) | `#HHH`; нет — `#110` | `id_port` |
| `NET_IP`, `NET_MASK` (Ethernet, обязательны) | десятичный адрес через точки | `local_ip`, `netmask` |
| `NET_GW` (Ethernet) | так же; нет — `0.0.0.0` | `gateway_ip` |
| `NET_MAC` (Ethernet) | `aa:bb:cc:dd:ee:ff`; нет — нули (адрес из PROM карты) | `mac` |
| `NET_BAUD` (ESP) | скорость NETUP; нет — 115200 | `uart_divisor` = 921600 / скорость, только целое (230400 → 4, 115200 → 8, 57600 → 16, 38400 → 24, 19200 → 48, 9600 → 96) |
| `NET_ESP_FLOW` (ESP) | ровно `3`: NETUP включил RTS/CTS с обеих сторон | `uart_flow` = 1, `esp_flow` = 3, бит `FLOW_VERIFIED` в `flags` |

Загрузчик всегда пишет `transport` (из A) и `cpu_khz` = 21000: у
Sprinter одна частота, игра это поле не заполняет. Переменную
`NET_ESP_FW` (версия прошивки модуля), DNS, `NET_RTL_TYPE` и
`NET_RTL_RESET` загрузчик не читает. Он проверяет только синтаксис.
Допустимость слота, выравнивание базы и порт ID проверяет INIT_CONFIG.

### Процедуры

| Процедура | Вход → выход | Портит |
|---|---|---|
| `UG_NETAUTO` | A = `UNETG_TRANSPORT_TCP` / `_UDP`, IX = блок, HL = профиль → CF = 0, A = `UGN_OK`; CF = 1, A = `UGN_E_*` | BC, DE, HL |
| `UG_NETENV` | A = протокол, IX = блок → CF, A = код, B = номер переменной | BC, DE, HL |
| `UG_NETUP` | IX = блок с полями карты, HL = профиль → CF, A = код, B / C | BC, DE, HL |
| `UG_NETFIX` | IX = блок: поля, которые игра знать не должна | AF |
| `UG_NETNAME` | IX = блок, DE = буфер 13 байт → имя `G<TCP\|UDP><ESP\|RTL\|509B>.DLL`; CF = 1 — не карта SDK | AF, B, DE, HL |
| `UG_NETVAR` | A = `UGN_V_*` → HL = имя переменной | AF, B |

Все сохраняют IX и IY. Вызывать их можно только в IM1, до `IM 2`, после
`UG_GW_INIT`. `UG_NETAUTO` — это `UG_NETENV`, затем `UG_NETUP`.

`UG_NETENV` пишет только перечисленные поля карты найденного типа и больше
ничего в блоке не трогает. Буфер значения — первые 256 байт региона
контекста: до INIT_CONFIG он свободен, и своей памяти у загрузчика нет.
DSS копирует значение без предела и отображает окружение в WIN3. Поэтому
регион должен быть не короче 256 байт и начинаться не выше `#BF00`,
иначе ответ `UGN_E_CFG`.

`UG_NETUP` работает и с блоком, который заполнила форма игры (как в
Headball, когда окружения нет). Порядок:

1. `UG_NETFIX`. Карта не ESP — `hw_ring_ptr` и `hw_ring_len` обнуляются:
   игра задаёт кольцо UART всегда, не зная карты. ESP — `esp_fw` = 0
   становится 1, а с `CFGF_UDP_RECORDS` — 2: одинаковые записи на любой
   карте означают прозрачный режим на ESP. `uart_rx_trigger` = 0
   становится 8, как в игровых профилях.
2. Имя DLL (`UG_NETNAME`) кладётся в регион контекста, затем `UG_LOAD`.
3. GET_INFO: DLL должна сообщить карту блока и иметь бит его протокола в
   `transports`. Иначе файл чужой или переименован: `UG_FREE` и
   `UGN_E_DLL`.
4. `UG_INIT_ENV`. При отказе — `UG_FREE`.

После любой ошибки `UG_NETUP` не оставляет загруженной DLL.

### Как игра выбирает протокол

Протокол — регистр A при вызове: `UNETG_TRANSPORT_UDP` или `_TCP`.
Загрузчик пишет его в поле `transport` и по нему выбирает `GUDP<карта>`
или `GTCP<карта>`. Для UDP формат на проводе задаёт флаг блока
`CFGF_UDP_RECORDS`:

- с флагом — записи с заголовком 2 байта на любой карте, на ESP это
  прозрачный режим (`esp_fw` = 2);
- без флага — обычные датаграммы, на ESP командный режим (`esp_fw` = 1).

### Коды

| Код | Значение | B, C |
|---|---|---|
| `UGN_OK` 0 | DLL загружена и сконфигурирована | — |
| `UGN_E_CFG` 1 | регион контекста меньше 256 байт или выше `#BF00`; в `UG_NETUP` — `hw_profile` не ESP / RTL / 3C509B | — |
| `UGN_E_NONET` 2 | `NET` нет или это не карта SDK (в том числе `LOOP`) | — |
| `UGN_E_ENV` 3 | переменной нет или значение испорчено | B = `UGN_V_*` (имя — `UG_NETVAR`) |
| `UGN_E_FLOW` 4 | ESP без `NET_ESP_FLOW=3` | B = `UGN_V_ESP_FLOW` |
| `UGN_E_LOAD` 5 | `UG_LOAD` отказал | B = `UG_LD_*`, C = `LIBMAN.l_reason` |
| `UGN_E_DLL` 6 | файл не той карты или не того протокола | — |
| `UGN_E_INIT` 7 | `UG_INIT_ENV` / INIT_CONFIG отказал | B = статус, `UGW_ENV` — какая проверка |

### Пример

```asm
	LD	A,SH_1FFD		; текущие значения #1FFD и #9FBD
	LD	E,SH_9FBD
	CALL	UG_GW_INIT
	LD	A,UNETG_TRANSPORT_UDP	; или UNETG_TRANSPORT_TCP
	LD	IX,net_cfg		; регионы, сроки, собеседник, порты, флаги
	LD	HL,net_profile		; профиль шлюза (UGP_*)
	CALL	UG_NETAUTO
	JR	NC,.net_ok
	CP	UGN_E_ENV		; переменная: её имя для сообщения
	JR	NZ,.no_net
	LD	A,B
	CALL	UG_NETVAR		; HL = "NET_IP" и т. п.
	...
.net_ok					; дальше как обычно: IM2, UG_START, ...
```

В блоке игра заполняет регионы (контекст, слоты, очередь, кольцо UART,
стеки, шлюз), сроки, `peer_ip`, `peer_port`, `local_port`, `flags`,
режим и бюджеты шлюза. Поля карты, `transport`, `cpu_khz`, `esp_fw` и
`uart_rx_trigger` она оставляет нулями.

| Часть | Байт кода |
|---|---|
| libman (уже нужен) | 1609 |
| `ugload.asm` (уже нужен) | 187 |
| `ugenv.asm` | 839 |
| `ugnet.asm` | 98 |

Памяти сверх уже нужных регионов загрузчик не берёт. Размеры проверяет
сборка (`ASSERT` в файлах, печать в `tools/build_sdk.sh`). Наибольшая часть

переменных (97 байт).

`ugenv.asm` и `ugnet.asm` нужны только при старте. Игра может поставить их
в память, которую потом отдаст под данные. NETDEMO V кладёт их в слоты
TX, которыми до первой отправки никто не пользуется: INIT_CONFIG пишет
только контекст. `ugload.asm` и libman должны остаться: `UG_FREE` нужен
при выходе.

## Шлюз

| Процедура | Где | Вход → выход | Портит |
|---|---|---|---|
| `UG_GW_INIT` | main, до прерываний | A, E = тени `#1FFD`, `#9FBD` | AF, BC, DE, HL |
| `UG_ATTACH` | main | A = страница, H = база | AF, HL |
| `UG_CALL` | main и ISR | B = экспорт; A, DE, IX, IY по ABI → A, DE, HL, F экспорта | BC |
| `UG_INIT_ENV` | main | IX = INIT_CONFIG, HL = профиль → A = статус, `UGW_ENV` | BC, DE, HL |
| `UG_START` / `UG_STOP` | main | периоды, допуск и входы ISR вкл. / выкл. | AF, HL |
| `UG_STEP` | main | → A = статус STEP или `UG_ST_EARLY/REFUSED/OFF`, DE, L | BC, HL |
| `UG_NOW` | main | → HL = `now_ms[15:0]`, DE = `[31:16]` | AF, B |
| `UG_TICK` | ISR таймера | такт: опрос, разнесение STEP, CBL, период | AF, DE, HL |
| `UG_ISR_NET` | ISR | A = источник | AF, BC, DE, HL |
| `UG_ISR_FRAME/KEY/CBL` | ISR | — | AF, BC, DE, HL |
| `UG_SHUTDOWN` | main | DE = предел, мс → A | BC, DE, HL |
| `UG_EXIT` | main, DI | → A = байт замка | HL |
| `UG_SNAPSHOT` | main | DE = буфер на 128 байт | AF, BC, DE, HL |

Все сохраняют IX и IY, кроме явно отмеченного; ни одна не пишет PIO и CTC.

**Прямой вызов.** `UG_CALL` переходит на `base + 0x20 + 3 × B`. Если в окне
DLL другая страница (игра держит там свои данные, или прерывание пришло в
середине работы игры), шлюз ставит страницу DLL и возвращает прежнюю.
Стоимость ~5 мкс вместо ~170 мкс у `l_call` с DSS SETWIN.

**`UG_INIT_ENV`** читает GET_INFO и профиль, считает бюджеты, стоимости и
квоты, заполняет поля INIT_CONFIG, принадлежащие шлюзу (`mode`,
`timing_mode`, `worst_poll_gap_us`, `worst_step_gap_ms`, `step_budget_us`,
`isr_budget_us`, `time_read_cost_us`, `isa_lock_ptr`, указатели теней), и
вызывает INIT_CONFIG. Остальные поля (карта, адреса, регионы, сроки, стек
ISR) задаёт игра.

| Поле профиля | Смысл |
|---|---|
| `UGP_TICK_US`, `UGP_TICK_FRAC` | Длина тика: целые мкс и 1/256 мкс |
| `UGP_PERIOD_TICKS` | Тиков в бюджетном периоде (10: период 19,99 мс) |
| `UGP_POLL_TICKS` | Тиков между гарантированными опросами (1; у Ethernet достаточно 10 — один опрос за период) |
| `UGP_STEPS` | STEP из квоты main за период |
| `UGP_STEP_GAP_MS` | Гарантированный худший разрыв между вызовами STEP |
| `UGP_CARD_N` | Входов IRQ карты за период (0: маршрута нет) |
| `UGP_STEP_BUDGET`, `UGP_ISR_BUDGET` | Бюджеты тел (0: `min_useful`, пустой опрос + возврат) |
| `UGP_Q_SERVICE` | Служебная квота за период |
| `UGP_TARGET` | Цель сети за период, настоящие мкс (ТЗ §5: 2000) |
| `UGP_OTHER_ISR` | Самый длинный чужой обработчик, мкс |
| `UGP_FLAGS` | `UGPF_RELAXED` (принять квоты выше цели), `UGPF_FRAME_PER` (период от кадра) |
| `UGP_MODE`, `UGP_TIMING` | `UNETG_MODE_*`, `UNETG_TIMING_*` |

Результат в `UGW_ENV`: `UG_ENV_OK` (сумма квот ≤ цели), `UG_ENV_OVER`
(выше цели, принят по `UGPF_RELAXED`), `UG_ENV_REFUSED`, `UG_ENV_GAP` (тик
опроса плюс 500 мкс DI плюс чужой обработчик больше `poll_gap_us`),
`UG_ENV_BUDGET`, `UG_ENV_INFO`, `UG_ENV_CONFIG` (INIT_CONFIG отказал,
A = его статус), `UG_ENV_PROFILE`.

**Допуск** (ТЗ §5.1). Квоты на период: опрос = опросов за период × стоимость
опроса, IRQ карты = `UGP_CARD_N` × стоимость опроса, main = `UGP_STEPS` ×
стоимость STEP, служебная — из профиля. Стоимость входа = бюджет тела +
обвязка шлюза; она списывается до входа и не возвращается.

- `UG_STEP` под одной короткой DI-секцией проверяет разнесение (не чаще
  одного STEP за `период / UGP_STEPS` тиков; ранняя попытка бесплатна) и
  квоту main, списывает полную стоимость и записывает активный вызов. STEP
  идёт без предзахвата ISA: ядро берёт замок на каждую порцию, звук не
  ждёт целый STEP.
- `UG_ISR_NET` проверяет срок опроса, затем замок и квоту источника и
  делает test-and-set замка (владелец 2). Занятая шина: стоимость `UG_BUSY_PATH_US`
  из квоты источника, ядро не вызывается, опрос остаётся должным
  (следующий источник — клавиатура или кадр — может его выполнить).
  Свободная: полная стоимость, стек ISR из INIT_CONFIG, `STEP_ISR` с
  признаком предзахвата, освобождение замка после возврата ядра.
- Отказ из-за квоты оплачивает служебная квота; IRQ карты при этом
  маскируется программно до опроса в следующем периоде.
- На границе периода каждая квота начинается заново, квота main — за
  вычетом полной стоимости ещё идущего STEP; остаток не переносится.

отказ через шлюз — 37,7 мкс, BUS_BUSY самого ядра — 55–57 мкс (GET_INFO 62).

**Сумма квот.** Все слагаемые — настоящие микросекунды: опрос стоит
136 + 25 + 70 мкс (пустой опрос и возврат из GET_INFO, путь шлюза), STEP —
его бюджет + 120 мкс, служебная квота 100.

| Опрос каждый тик, 2 STEP минимального бюджета | 4670–4792 мкс | — |

Цель ТЗ §5.1 (≤ 2000 мкс) не выполняет ни один профиль; `UGW_ENV` =
`UG_ENV_OVER`, нужен `UGPF_RELAXED`. Профиль игры — `UGP_POLL_TICKS` = 10,
`UGP_STEPS` = 1, `UGP_STEP_BUDGET` = 2000: карта Ethernet сама хранит
принятые кадры, и опрашивать её из каждого тика незачем (`poll_gap_us`
всех сборок с картой — 25 000 мкс). У SprinterESP профиль тот же, но опрос
стоит сделать двигающим байты UART: `UGP_ISR_BUDGET` = 341 (до 12 байт за
опрос), сумма квот 2631 мкс.

**SprinterESP.** Обмен с модулем идёт командами AT: один маленький пакет —
это около 100 байт через UART и два обмена с модулем (приглашение и
`SEND OK`). Бюджет STEP для игры — 2000 мкс: с бюджета около 1800 мкс STEP
делает несколько порций UART и разбирает ответы модуля целиком («толстый
STEP», `docs/MEASUREMENTS.md`), при меньшем — одну порцию и один разбор.
Через шлюз, один STEP на 2000 мкс за период, опрос каждый тик (стенд Z,
`tools/dev/sdk_lat.js`; мс до TX_DONE / до эха, в скобках — расход сети на
период в среднем):

| Пакет | `UGP_ISR_BUDGET` 0 (опрос не двигает байты) | `UGP_ISR_BUDGET` 341 (до 12 байт за опрос) |
|---|---:|---:|
| GUDPESP, 16 байт | 112 / 181 (3,1 мс) | 54 / 81 (3,3 мс) |
| GUDPESP, 64 байта | 175 / 382 | 115 / 146 |
| GTCPESP, 16 байт | 112 / 339 | 54 / 199 |
| GTCPESP, 64 байта | 173 / 504 | 116 / 261 |

До толстого STEP тот же пакет в 16 байт без шлюза занимал 240 / 282 мс
(12 и 14 кадров). Опрос в каждом тике стоит около 2,1 мс на период сам по
себе, и в 2,5 мс на кадр эти профили не помещаются. С 22.11.2026
`poll_gap_us` сборок ESP — 25 000 мкс (было 2500): FIFO UART останавливает
модуль через auto-RTS, и редкий опрос ничего не теряет (остановка потока
по RTS на плате подтверждена пользователем). Профиль игры для ESP — один
STEP на 2000 мкс и один-два опроса на 341 мкс за период (мс до TX_DONE /
до эха):

| Профиль (`UGP_STEPS` 1, `UGP_STEP_BUDGET` 2000, `UGP_ISR_BUDGET` 341) | Сумма квот | GUDPESP, 16 байт | GUDPESP, 64 байта | GTCPESP, 16 байт | Расход сети на период |
|---|---:|---:|---:|---:|---:|
| `UGP_POLL_TICKS` 10 (один опрос за период) | 2631 мкс | 74 / 119 | 134 / 257 | 74 / 258 | 1,7 мс в среднем, до 2,2 |

Состояние игры через ESP выгоднее слать одним маленьким пакетом раз в
несколько кадров, а не каждый кадр: темп в обе стороны одновременно — 9–12
пакетов по 16 байт в секунду (`docs/MEASUREMENTS.md`, «Что получает игра
при одном STEP за кадр»).

**Прозрачный UDP (GUDPESP, `esp_fw` = 2, с 22.11.2026).** Модуль держит
режим данных, команд AT на пакет нет; каждая датаграмма — запись с
заголовком 2 байта, и сервер игры обязан разбирать их как поток
(`docs/unet-game-abi.md`, «Прозрачный режим UDP»; эталон —
`tools/mame/echo_server.py --framed`). Профиль игры для него — один STEP
на 3000 мкс и **два** опроса на 341 мкс за период (`UGP_POLL_TICKS` 5),
порог FIFO 8: поток Headball — 18,7 ввода по 20 байт и 10 снимков по 88
байт в секунду, ввод до 100 мс, около 1,9 мс сети на кадр; ввод до 15
байт — 25 в секунду. В командном режиме тот же профиль даёт 5 вводов в
секунду. CLOSE в этом режиме длится ~1,4 с, SHUTDOWN ~1,5 с: держите
`close_timeout_ms` не меньше 1500; потерю связи модуль не сообщает —
живость проверяет игровой протокол.

Задержка пакета и расход на кадр для любого профиля —
`node tools/dev/sdk_lat.js [--steps n] [--budget мкс] [--polls тиков]`.

Пропускная способность через шлюз зависит от числа STEP за период
(`node tools/dev/sdk_rate.js [--budget us] [--isr us]`, эхо 2 КиБ в обе
стороны, стенд Z, минимальный бюджет, опрос каждый тик):

| STEP за период | GTCPRTL | GTCP509B | GUDP509B | GTCPESP | GUDPESP | Сумма квот |
|---:|---:|---:|---:|---:|---:|---:|
| 2 | 0,59 КиБ/с | 0,61 | 0,96 | 0,18 | 0,27 | 4670–4792 мкс |
| 5 | 1,51 | 1,59 | 2,40 | 0,44 | 0,68 | 8060–8365 мкс |
| 10 | 3,02 | 3,13 | 4,79 | 0,88 | 1,35 | 13 710–14 320 мкс |

Бюджет STEP по умолчанию — опубликованный минимум (одна самая дорогая
статья за шаг). `UGP_STEP_BUDGET` можно поднять до
`GET_INFO.step_body_max_us` (3000 мкс; до 22.11.2026 — 2000).

**Выбор бюджета STEP.** Бюджет — это наибольшая длительность одного вызова,
на которую согласна игра, в **настоящих микросекундах платы** (с 22.11.2026;
поправку на ожидания памяти делает ядро, игра ничего не измеряет и
передаёт `cpu_khz` = 21000). Диапазон — от `min_useful_budget_us`
(1047–1076 мкс у карт) до `step_body_max_us` (3000 мкс). При минимальном бюджете в
STEP помещается одна единица работы, а постоянная часть вызова (480–560 мкс)
платится каждый раз; при большем бюджете ядро делает за вызов несколько
единиц. Число STEP до TX_DONE и до прихода эха одного пакета 64 байта
(стенд Z в настоящем времени, `tools/dev/pkt_steps.js`):

| Сборка | минимум | 1500 мкс | 2000 мкс |
|---|---:|---:|---:|
| GUDP509B | 24 / 22 | 6 / 11 | 3 / 6 |
| GTCP509B | 20 / 30 | 12 / 18 | 6 / 10 |
| GUDPRTL | 26 / 24 | 8 / 11 | 4 / 7 |
| GTCPRTL | 24 / 34 | 14 / 20 | 7 / 11 |
| GUDPESP | 46 / 56 | 21 / 30 | 17 / 24 |
| GTCPESP | 45 / 93 | 21 / 44 | 16 / 32 |

Ядро выдерживает бюджет: самый долгий вызов при бюджете 2000 мкс —
1500–1715 мкс. Длинный STEP задерживает только главный цикл: секции с
запретом прерываний не длиннее 444 мкс при любом бюджете
(`GET_INFO.max_atomic_us`). Сколько стоит пакет и почему — в
`docs/MEASUREMENTS.md`, «Единица бюджета и настоящее время».

**Маленькие пакеты (GUDP509B, с 22.11.2026).** При бюджете STEP от
примерно 1800 мкс сборка GUDP509B ведёт маленькую датаграмму коротким
путём: отправка до 64 байт — одна программная статья и два захода на шину
вместо шести, приём датаграммы до 22 байт — один заход и одна статья. При
одном STEP на 2000 мкс за кадр датаграмма до 16 байт выходит в провод за
2 STEP и её эхо читается через 3 STEP (обычным путём — 3 и 5); через шлюз
SDK в профиле игры это 33 мс до TX_DONE и 57 мс до эха в среднем. Игре,
которой важна задержка, стоит укладывать пакет состояния в 16 байт
(22 — предел короткого приёма). Пакеты крупнее идут обычным путём; у
остальных сборок короткого пути нет — в бюджете 2000 мкс он там ничего
не даёт (`docs/MEASUREMENTS.md`, «Короткий путь»).

## Адаптеры времени

`now_ms` хранится в блоке шлюза; основной цикл читает его через `UG_NOW`.

- **FIXED_SCHEDULE.** Тик прибавляет свою настоящую длину: целые мс и
  остаток в мкс заранее разложены `UG_INIT_ENV`, доли мкс — в байте
  1/256. Счётчики во время игры не читаются. На стенде Z за 20 с ошибка
  ≤ 2,5 мс (фаза тика при чтении); в MAME — 1,000 мс `now_ms` на мс.
- **APP_COUNTER** (цепь CTC2 → CTC3 игры, 875 кГц, /112, /156). Тик читает
  CTC3, CTC2, CTC3; при смене CTC3 — ещё одно чтение, при второй смене
  отметки нет (следующий тик догонит). Фаза берётся из двух таблиц по
  значению CTC3, дельта по модулю 17 472 публикуется как 32-битный счётчик
  отсчётов (только ISR). В мс его переводит `UG_NOW` в основном цикле.
  Стоимость выборки с повтором ≤ 17,8 мкс (норматив 20). Адаптер только
  читает CTC; программирует цепь игра. В MAME holub цепь на 875 кГц не
  считает, поэтому APP_COUNTER проверен только на стенде Z.

## Пример NETDEMO

`sdk/example/netdemo.asm` → `NETDEMO.EXE` (DSS). Карта WIN2
(`tools/mame/mkcfg.js --prog netdemo`): код с `0x8100`, контекст `0x9C00`,
слоты TX/RX, очередь событий, кольцо UART `0xB040`, блок шлюза `0xB300`,
таблица IM2 `0xB400` (I = `#B4`, байт `#B5`, обработчик по умолчанию
`0xB5B5`), стек ISR `0xB600`, отчёт `0xB700`, главный стек `0xBB00..0xBFF0`.
Тик — CTC1, кадр (`#FF`) только считается и даёт дополнительную возможность
опроса. Секундомер на CTC2/CTC3 (таймер /16) пишет строку `TIMING`.

Сценарии (`-DSCEN`): L — загрузка, сверка, освобождение; E — эхо 300 байт;
S — поток 8 КиБ; P — сервер закрывает соединение; D — SHUTDOWN при
открытом канале; W — пауза 2 с между двумя эхо; V — эхо, как E, но через
`UG_NETAUTO`: блок `mkcfg.js --auto` без полей карты, на стенде M
окружение программа ставит сама (DSS `#46 B=2`), строка `AUTO`.
`-DUG_STEPS=n` — STEP за период. Запуск:
`tools/mame/run_m.py --prog netdemo gtcpesp E`.

## Ограничения v1

- Маршрута IRQ карты к PIO нет ни на одной известной плате, ни в MAME;
  шлюз не пишет PIO и IM2 маршрута, `MASK_ROUTE` и исчерпание квоты карты
  ставят только программную маску. Ядро обслуживает AUTO через POLL, пробы
  IRQ нет (`CAP_PROBE` не публикуется).
- Граница пути ISR по бюджетам (тело STEP_ISR 161 + обвязка 70 + такт,
  часы, вход и RETI 115) — 346 мкс настоящего времени, замер 281–291 мкс;
  цель ТЗ §3 (≤ 200 мкс) не выполняется.
- В MAME тиковый ISR занимает 299–318 мкс, допущенный `UG_STEP` вместе с
  прерывающим его тиком — до 2,2 мс при бюджете 2000 мкс (см. MEASUREMENTS).
- Кадровый импульс FPGA (~9 мкс в MAME) теряется под DI; источник периода —
  таймер. Переключение на кадр (`UGPF_FRAME_PER`) — после замера на Ж.
- Ядро не держит разрыв STEP 20 мс у TCP-сборок (MEASUREMENTS, долг).

## Пропускная способность ESP: `UGP_ISR_BUDGET`

На профиле SDK по умолчанию (`UGP_ISR_BUDGET` 0: тело STEP_ISR = пустой
опрос + возврат, 161 мкс) STEP_ISR у SprinterESP не переносит байты —
остатка бюджета на это нет (ядро: `ES_ISRCAP`, docs/ARCHITECTURE.md,
«Насос приёма в STEP_ISR»). Игра, которой важна скорость ESP (ТЗ §6.1:
2048 Б/с полезных данных в каждую сторону), поднимает `UGP_ISR_BUDGET`:
перенос n байт требует бюджета 245 + 8 × n мкс (341 мкс для 12 байт —
наибольшая порция; предел `isr_body_max_us` — 370 мкс). Сумма квот при
этом растёт на прибавку бюджета за каждый опрос. Замеры скорости сделаны
до перехода на настоящее время (бюджеты 65 / 120 / 150 единиц, то есть
161 / 296 / 370 мкс; `tools/dev/sdk_rate.js --isr`, docs/MEASUREMENTS.md
«Этап ESP 2 КиБ/с»): GUDPESP при 5 STEP за период 0,68 → 0,99 КиБ/с,
GTCPESP 0,44 → 0,53. Цель §6.1 на стенде Z достигается у GUDPESP при
прямом измерении потока с наибольшим бюджетом STEP_ISR — у GTCPESP нет
(2020 Б/с): пассивное чтение TCP ждёт
`CIPRECVDATA`, которую выдаёт только main-STEP, поэтому второй дренаж
STEP_ISR не успевает набрать байты до конца этого обмена.
