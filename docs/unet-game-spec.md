# ТЗ UNET-GAME — игровые сетевые библиотеки для Sprinter

Дата: 2026-10-30. Статус: требования к разработке и приёмке; реализация и
аппаратные измерения по этому документу ещё не выполнены.

Документ фиксирует согласованную основу игрового варианта UNET и уточняет
поддержку IRQ, обязательную работу через опрос и совместное обслуживание из
нескольких источников прерываний. Наличие IRQ не является условием поддержки
сетевой карты. Существующие блокирующие экспорты UNET нельзя вызывать из ISR;
описанный ниже `STEP_ISR` — новый ограниченный по времени вход.
Нормативное приложение: [ABI v1](unet-game-abi.md). Оно определяет контракт
профилей, памяти, очередей, событий и сроков, общий для всех сборок.

## 1. Назначение и состав

Обеспечить сетевую игру, чат и обмен с сервером без остановки игрового цикла,
звука и ввода. Первое приложение — Worms: два игрока через отдельный сервер,
наблюдатель подключается к серверу и не создаёт дополнительный канал на Z80.
Турнирный протокол, чат и сервер реализуются поверх библиотеки.

Поставить шесть профилей из общего ядра: ESP/TCP, ESP/UDP, RTL8019AS/TCP,
RTL8019AS/UDP, 3C509B/TCP, 3C509B/UDP. Седьмой транспорт — loopback с тем же
ABI для проверки игрового кода без карты. В первой версии достаточно одного
соединения TCP либо одного выбранного партнёра UDP.

Для каждой аппаратной сборки обязательны работоспособный `POLL` и запуск в
`AUTO` без линии IRQ. Это условие выпуска. IRQ квалифицируется дополнительно
для конкретного сочетания карты, платы и слота. Без проверенного маршрута
допускается выпуск POLL-only: `GET_INFO` сообщает отсутствие квалифицированного
IRQ, а `AUTO` работает через опрос. Маршрут не объявляется рабочим по схеме.
Общий исходный код и ABI должны иметь единую версионируемую точку разработки;
копии ядра в трёх репозиториях не являются независимыми источниками истины.

## 2. Базовые ограничения библиотеки

- Каждый профиль поставляется как DLL формата L1 для libman 1.3. Файл проходит
  две проверки размера. Загружаемый префикс должен помещаться в 16 384 байта,
  и сумма размера распакованного образа (включая 32-байтовый заголовок)
  и размера таблицы релокаций должна помещаться в те же 16 384 байта.
  Код, таблицы и обработчик IRQ входят в образ. Холодные оверлеи во время игры запрещены.
  Контекст, RX/TX-буферы и стек вызывающего, включая стек прерываний, выделяет
  приложение в постоянно видимой памяти вне окон ISA и кода библиотеки.
  Собственного стека у ядра нет; области и глубина проверяются по ABI.
  Отчёт сборки показывает размеры образа и таблицы релокаций отдельно,
  их сумму и размер префикса из заголовка L1.
- Для 3C509B/TCP достижимость 16 КБ подтвердить сборкой прототипа до основной
  реализации TCP: перенос одного BSS за пределы страницы недостаточен при
  сохранении существующего холодного оверлея.
- Ядро не вызывает DSS, BIOS и libman, включая инициализацию и обработку ошибок.
  Загрузчик SDK до боя размещает и релокирует DLL по правилам libman,
  обслуживает загрузочный вход INIT и сохраняет страницу и фактическую базу
  для прямого вызова игровых экспортов. `INIT_ENV` готовит двоичный блок
  для `INIT_CONFIG`. Во время боя шлюз вызывает экспорты в том окне, для
  которого выполнена релокация. Это сохраняет бюджет ISR и не требует DSS.
- DNS, PING, LISTEN, файловые операции, терминал, второй канал и текстовый
  разбор окружения не входят в обязательное игровое ядро. Адрес партнёра,
  параметры сети и срок действительности конфигурации передаёт приложение.
- Все ожидания аппаратуры, подключения, передачи и закрытия оформляются
  возобновляемыми состояниями. Парсер ESP сохраняет состояние после любого
  байта, в том числе посреди заголовка `+IPD`. Самомодифицируемый код запрещён.
- Протокольные часы — передаваемое приложением 32-битное `now_ms`, которое
  продолжает идти в паузе. Сравнения выдерживают переполнение счётчика;
  отдельные интервалы должны быть меньше половины его диапазона.
- На Ethernet проверять входящие IPv4/TCP и ненулевые UDP checksum; нулевая
  UDP checksum допустима для IPv4. Ошибки учитываются и не выдаются приложению
  как корректные данные. У ESP проверку IP/TCP/UDP выполняет прошивка;
  библиотека отдельно контролирует целостность UART-обмена и границы сообщений.
- ARP-ответчик обслуживается постоянно, включая простой соединения. Требуются
  кэш next-hop, обновление до истечения и повторное разрешение после исчерпания
  повторов. Отбрасывание чужих кадров также выполняется порциями, без ожидания
  окончания аппаратной команды в одном вызове.
- Собственный IPv4/TCP: MSS до 536 байт, не более двух сегментов в полёте,
  без искусственной задержки Nagle; при заполнении RX уменьшается окно.
  UDP: до 512 байт, датаграмма принимается или отбрасывается целиком.
  Собственная сборка IP-фрагментов не поддерживается. Границы возможностей
  прошивки ESP, размеры слотов и обращение с переполнением — в ABI.

## 3. Модель API и владение состоянием

Настройку выполняет `INIT_CONFIG`, работу обслуживают `STEP` и `STEP_ISR`.
Приложение использует `OPEN`, `TX_RESERVE`/`TX_COMMIT`/`TX_UNRESERVE`,
`RX_PEEK`/`RX_RELEASE`, `NEXT_EVENT`, `CLOSE`, `ABORT`, `GET_INFO` и
`GET_STATS`. Экспорт `SHUTDOWN` завершает работу контекста из основного цикла
по правилам §3 ABI. Операции очередей не ожидают сеть. У TX есть
тег приложения, возвращаемый с результатом освобождения слота. TCP — поток;
его границы сообщений определяет игровой протокол. Для UDP сохраняются границы
датаграмм и фильтрация по выбранному партнёру; смена партнёра — через CLOSE/OPEN
без повторной инициализации всей библиотеки.

`STEP(now_ms, budget_us)` выполняется в основном цикле: разбирает протокол,
считает checksum порциями, обслуживает таймеры и продолжает отложенные операции.
Статусы: `WORK`, `YIELD`, `IDLE`, `BUS_BUSY`. Возврат ближайшего протокольного
срока в миллисекундах не заменяет отдельный срок аппаратного опроса: даже при
отсутствии таймеров и значении `0xFFFF` входящие данные нужно обнаруживать.
Только STEP продвигает протокольные таймеры, в том числе во время паузы.
`GET_INFO.max_step_gap_ms` задаёт отдельный предел между результативными
протокольными шагами (игровой профиль: 20 мс). Ни IRQ, ни пустая попытка
STEP с недостаточной квотой не заменяют эту работу.

`STEP_ISR(source, budget_us)` — единственный вход ядра, разрешённый из ISR.
Он обслуживает только ограниченную порцию аппаратного ввода-вывода и публикует
отложенную работу. Для UART это FIFO ↔ программные кольца и состояния ошибок;
для Ethernet — причина IRQ, подтверждение/маскирование и допускаемая профилем
порция обмена. Полный пакет, TCP, checksum и разбор AT-ответа не обрабатываются
целиком в ISR. Оба входа используют один автомат аппаратного обмена; параллельные
независимые читатели UART или NIC запрещены.

`source` различает аппаратный IRQ карты, таймер, кадр, клавиатуру, CBL и другие
зарегистрированные источники. Это основание для ограничений и статистики,
а не разрешение выдать каждому источнику новый бюджет. Для CBL SDK по умолчанию
лишь устанавливает флаг ожидающего обслуживания, не вызывает ядро.

Все остальные экспорты вызываются из основного цикла. ISR не вызывает игровой
код и callback приложения. Обмен данными идёт через очереди с единственным
производителем и потребителем. Предпочтительны однобайтовые индексы SPSC:
производитель записывает содержимое и только затем публикует индекс одной
записью; для кольца на 256 позиций с пустым сторожевым слотом вместимость 255.
Многобайтные индексы (например, кольцо UART на 512 байт) требуют атомарной
публикации и чтения либо эквивалентного протокола. При заполнении очереди
событие освобождения TX нельзя терять: завершение удерживается до публикации.

Библиотека не использует теневые регистры Z80, сохраняет IX/IY, не выполняет
EI из ISR. В v1 сетевой ISR невложенный: вход и выход при IFF=0, RETI и
восстановление контекста принадлежат шлюзу. Норматив всего пути **с вызовом
сетевого ядра** от принятия IRQ до возврата — 200 мкс; тела STEP_ISR — не более 150 мкс и только в
оставшемся сроке (§5). Если собственный обработчик уже исчерпал его, сетевое
тело не вызывается. Стек тела ≤96 байт; вместе с обвязкой/входом CPU ≤160.

## 4. Конфигурация IRQ и обязательный fallback

### 4.1. Режимы

| Режим | Контракт |
|---|---|
| `POLL` | Прерывания сетевой карты отключены; все операции доступны через гарантированный периодический опрос |
| `AUTO` | Начинает с POLL; использует IRQ только при известном разрешённом подключении, постоянно сохраняя резервный опрос |

По умолчанию используется `AUTO`. Если описание подключения отсутствует,
PIO занят несовместимым владельцем либо маршрут IRQ не поддержан, фактический
режим остаётся `POLL`. Строгого режима «только IRQ, без опроса» в v1 нет.

`INIT_CONFIG` должен содержать версию/размер блока, выбранный режим, профиль
карты и её адреса, описание доступного маршрута IRQ и гарантии обслуживания
приложением. Для ESP дополнительно передаются скорость UART, профиль прошивки
и состояние управления потоком на обеих сторонах. Числа хранятся little-endian,
IP-адреса — в сетевом порядке; раскладка фиксируется в общем include ABI.

Платформенный шлюз SDK владеет настройкой PIO/IM2 и тенями системных портов.
Маршрут включает группу ISA, вход PIO, выделенный вектор и допустимые маски.
Библиотека не сканирует произвольные векторы и не угадывает разводку.
Номер IRQ на контакте ISA не следует считать самостоятельным вектором Z80.

В Sprinter предусмотрен приём ISA IRQ через PB0/PB1 PIO Z84C15. У SprinterESP
v1.0.5 выход INTR UART соединён с IRQ3/B25 ISA. Это подтверждает возможность
реализации, но не заменяет проверку конкретной платы, слота и адаптера.
Сохранение направления и уровней PB6/PB7, DACK и масок других источников
обязательно: PIO B используется также вторым Sega-джойстиком через LPT.
Все управляющие слова PIO, включая настройку Sega, проходят через одного
владельца. В режиме 3 слово управления с «mask follows» и следующий байт
маски пишутся подряд под одним DI из общей программной тени, без другого
писателя между OUT. Сохраняется входное состояние IFF.

### 4.2. Работа резервного опроса

Опрос проверяет непосредственно регистры состояния/FIFO/кольцо карты;
проверка одного флага от ISR не считается fallback. Он выполняется с первого
момента разрешения приёма, включая инициализацию, ожидание подключения и паузу
игры. Профиль публикует три *верхние границы*, включая ожидание занятой шины:
`poll_gap_us` для POLL и ещё не проверенного AUTO; `auto_fallback_gap_us`
для резервного опроса после проверки IRQ; `max_service_gap_us` — физический
предел для этого сочетания скорости, буфера и управления потоком. Требовать
`poll_gap_us ≤ auto_fallback_gap_us ≤ max_service_gap_us`. Второй интервал
может быть больше первого лишь после проверки потери IRQ при полной допустимой
нагрузке. При fallback сразу действует первый срок; BUS_BUSY его не продлевает.

При физически отсутствующей линии обмен должен начаться и продолжаться через
опрос. Во время работы пропущенный IRQ не должен оставлять RX/TX без движения
до следующего случайного пользовательского ввода или протокольного таймаута.

При каждом INIT путь начинается в POLL. Проба выполняется до OPEN, только для
разрешённого маршрута и при наличии безопасной команды профиля: например,
UART TX-empty с проверкой IIR или передача тестового кадра в loopback NIC.
Шлюз ставит обработчик, убирает старую причину и разрешает только пробный
источник; ядро создаёт известную причину. Проба — состояние автомата, без
ожидания в INIT/ISR. Окно наблюдения `irq_delivery_us ≤ poll_gap_us` задаёт
профиль. Шлюз должен гарантировать проверку к концу этого окна даже при
отсутствии IRQ карты. Если расписание игры этого не позволяет, AUTO остаётся в POLL.
На IRQ источник сразу маскируется; успех требует совпадения вектора, группы
и причины в карте, ложный/удерживаемый сигнал не засчитывается. На таймауте
маскируют маршрут, снимают причину и продолжают POLL. Успех не кешируется
между запусками. При отсутствии безопасной пробы профиль остаётся POLL-only.
На квалификационном стенде кандидат задаётся явно до публикации возможности
IRQ; это не разрешает перебор входов PIO на компьютере пользователя.

В AUTO обозначим `A = auto_fallback_gap_us`, `D = irq_delivery_us`.
Готовые данные начинают обслуживаться при первом полезном резервном опросе,
не позднее A от их появления. Подтверждать неисправность перед чтением не
требуется. Это срок доступа к карте, публикация RX в приложении учитывается отдельно.

Для причины с известным временем появления и разрешённым маршрутом отсутствие
доставки проверяется после окна D. Следующий резервный опрос переводит маршрут
в POLL не позднее D + A от начала этой причины. Для обычного RX без временной
метки применяется отдельное правило двух наблюдений. Две последовательные
находки новых ожидающих IRQ-причин при разрешённом источнике и неизменном
счётчике доставленных IRQ приводят к переходу в POLL сразу на второй находке.
При устойчивой нагрузке с новой причиной к каждому опросу предел от начала
такой нагрузки равен 2 × A. При A = 5000 мкс, D = 2000 мкс стенд проверяет
соответственно 5 мс для первого обслуживания, 7 мс для причины с известным
началом и 10 мс для двух наблюдений. Отдельного ожидания D после второй
находки нет. При редком трафике второй причины может ещё не быть.

Действительный IRQ или опрос без причины прерывает последовательность.
Собственная маска и BUS_BUSY исключаются из наблюдений о доставке. Запоздалый
IRQ перепроверяет карту и не читает байт повторно. В открытом канале маршрут
помечается «доставка не подтверждена» без разрушающей пробы.

Переход IRQ → POLL не сбрасывает карту, парсер, очереди и TCP/UDP-состояние,
не меняет скорость UART и не закрывает соединение. Уже повреждённый UART-поток
восстанавливается по отдельному пути ошибки, а не скрывается сменой режима.
После отключения неисправного IRQ автоматические повторные включения в каждом
кадре запрещены; повторная проба — только по явному запросу из основного
цикла вне открытого канала. Текущая сессия продолжает работу через опрос.

### 4.3. Подтверждение, маскирование и восстановление IRQ

Ядро владеет масками **в карте** (UART IER, RTL IMR, маски 3C509B) только
при захваченной ISA. Оно возвращает отдельный флаг `MASK_ROUTE`, если причину
нельзя снять в срок. Только шлюз маскирует **маршрут PIO** и меняет IM2;
он может сделать это и без входа в ядро. Простой возврат `BUS_BUSY` при удерживаемой линии
недостаточен: он не должен порождать непрерывные повторные входы в ISR.

Если ISA занята, шлюз использует доступную без ISA маску нужного источника PIO,
сохраняя остальные источники. После освобождения шины обслуживание продолжается
через опрос. Перед повторным разрешением IRQ проверяются состояние карты и
новые события; тестировать приход события между проверкой и разрешением.
Для общей линии требуется диспетчеризация без отключения чужих источников;
если профиль этого не обеспечивает, сетевой драйвер работает через `POLL`.

Звук, сеть, другие ISA-драйверы и основной цикл используют один байт
`INIT_CONFIG.isa_lock_ptr` в постоянно видимой RAM. Владелец и значения
зафиксированы в [ABI](unet-game-abi.md). Захват даже своим владельцем не
рекурсивен. Если шлюз захватил ISA при допуске, он передаёт право доступа
только текущей порции ядра и сам освобождает замок при её возврате (§1 ABI).
Проверка и захват
выполняются атомарно в короткой DI-секции с восстановлением входного состояния
IFF; неатомарный test-then-set запрещён. Тени write-only портов `#1FFD` и
`#9FBD` предоставляются шлюзом приложения. Восстанавливаются точные прежние
значения и страницы памяти, а не константа `#01` или ноль.

## 5. Разные прерывания и общий бюджет

| Источник | Разрешённая работа |
|---|---|
| IRQ карты | Короткий STEP_ISR: аппаратное событие и ограниченная порция обмена |
| Периодический вызов приложения | Гарантированный опрос по сроку и продолжение отложенного обмена. Подходит уже используемый таймер или работа с проверенным интервалом в основном цикле |
| Кадр | Дополнительное обслуживание при наступившем сроке и свободном бюджете |
| Клавиатура и другие редкие IRQ | Дополнительная возможность, не источник гарантированной периодичности |
| CBL / частый звуковой IRQ | По умолчанию только флаг; аппаратный обмен — лишь в отдельно измеренном профиле с соблюдением звукового срока |
| Основной цикл | STEP и добор аппаратной работы из того же бюджета |

В каждом обработчике сначала выполняется обязательное обслуживание его
собственного устройства. Сетевой шлюз затем проверяет pending/срок опроса,
остаток общего бюджета, допустимый бюджет данного источника и занятость шины.
Бессмысленные повторные опросы из всех ISR подряд запрещены.

Целевой бюджет интеграции Worms — **не более 2 мс на аппаратный видеокадр**
для всей сети: IRQ, резервный опрос, STEP, учёт, отображение страниц,
подтверждение/маскирование и дополнительная стоимость сетевых входов в ISR.
Бюджет сбрасывается один раз при смене аппаратного кадра, независимо от
логических шагов игры, паузы и числа вызовов. Неиспользованный остаток не
накапливается после задержанного кадра. У тестового приложения без видео
период учёта задаётся таймером 20 мс и явно отмечается в отчёте.

### 5.1. Допуск в v1: фиксированные квоты

SDK при INIT выделяет части одного кадрового бюджета обязательному опросу, IRQ карты,
main и служебным входам. Их сумма ≤2000 мкс. Квоты не перераспределяются
внутри кадра. До входа списывается **квалифицированная верхняя стоимость**
порции, включая шлюз, проверку часов, try-lock, сохранение страниц, маску и
возврат. Для порции, начинающейся с доступа к ISA, разрешён отдельный отказ
по занятой шине до входа в ядро. Шлюз под одним коротким DI проверяет квоту,
владельца и атомарно списывает стоимость выбранного пути. Для занятой шины
это квалифицированная константа `busy_path_us`, включая проверку, маскирование
удерживаемого IRQ при необходимости и возврат. Для свободной шины полный
дебет и захват выполняются вместе, только если хватает квоты. Если времени
мало, оплачивается квалифицированный служебный отказ без захвата. BUS_BUSY
из-за занятой ISA оплачивает квота источника вызова, включая маскирование,
если оно входит в этот путь. Отказ в допуске из-за недостатка квоты источника
целиком оплачивает служебная квота. За один отказ списывается одна стоимость.
При отсутствии
замера занятого пути используется полный дебет. После допуска в ядро стоимость
порции сохраняется при BUS_BUSY, IDLE и раннем возврате, скидки по измеренному
времени нет. Отказ до входа не засчитывается как опрос или протокольный шаг.
Измеренное время — диагностика и проверка верхних оценок, не источник кредита.
Динамический резерв с возвратом остатка не входит в v1.

Квота обязательного опроса закреплена за периодическим вызовом приложения
и доступна даже после шквала IRQ. Перед исчерпанием
IRQ-квоты шлюз маскирует маршрут и оставляет pending; в следующий период
проверяет карту через опрос и лишь затем разрешает IRQ. Обработка CBL-флага
также входит в служебную квоту. Для каждого включённого
хука профиль ограничивает число входов; если это невозможно, хук не ставится.
Короткий путь маскирования должен иметь заранее зарезервированное время.

Номер периода даёт аппаратная кадровая шкала шлюза, даже если отрисовка
пропустила кадр. Обновление квот и записей об активных вызовах атомарно.
На границе новый период начинает каждую квоту за вычетом *полных верхних
стоимостей ещё активных вызовов* своего источника. Так вызов, пересёкший
границу, консервативно оплачен в обоих кадрах. Возврат только снимает запись
об активности, но не пополняет квоту. Промежуточные пропущенные периоды не
накапливают кредит. Это правило относится и к main, прерванному аппаратным IRQ.

| Ограничение | Включённая работа и предел |
|---|---|
| STEP | Тело ≤500 мкс и ≤переданного бюджета; полная стоимость с обвязкой списывается из квоты main |
| STEP_ISR | Без вложенного EI. Тело ≤150 мкс, полный непрерывный путь с шлюзом и RETI ≤200 мкс |
| Общий DI | Любая непрерывная секция сети ≤200 мкс; ранее потраченное под DI время устройства и более строгий срок аудио вычитаются **до** входа |
| Пустой опрос / BUS_BUSY | Тело ≤100 / ≤25 мкс соответственно, всегда в пределах остатка бюджета |

Допуск тела ISR = min(150 мкс, квота вызова минус обвязка, допустимый остаток
DI до RETI, запас до звукового срока). Если времени мало, допускается только
дешёвый YIELD либо маскирование шлюзом. GET_INFO публикует минимальную стоимость
возврата, `min_useful_budget_us` и `max_atomic_us`: неделимую операцию нельзя
начать, если она вместе с возвратом не помещается. Все числа — требования к
прототипу, а не результаты замеров.

### 5.2. Время приложения и звук

Каналы CTC, их делители, векторы и обработчики принадлежат приложению.
UNET-GAME обходится без выделенного канала. Ядро не обращается к портам CTC.
Шлюз использует только те ресурсы времени, которые явно предоставил владелец.
Это правило действует и при INIT, пробе IRQ, ошибке и выходе.

Приложение передаёт в STEP монотонное `now_ms` для сроков протокола и
обеспечивает периодический опрос карты даже во время паузы. Это независимые
задачи. Например, игра может считать миллисекунды своим системным тиком,
а порции опроса запускать в уже существующем обработчике после его основной
работы. Допускается и вызов из основного цикла, если измерен худший интервал
с учётом отрисовки, паузы и занятой ISA. Частота тика сама по себе этого не гарантирует.

SDK поддерживает два способа допуска порций к исполнению.

- `APP_COUNTER` использует точную монотонную шкалу, которую предоставляет
  игра. Адаптер шкалы находится в шлюзе. Он может читать уже настроенный
  счётчик с разрешения владельца либо получать равноценную метку из другого
  источника. Частота, период переполнения и стоимость чтения описываются
  для выбранного источника. Предельный квант 2 мкс, стоимость чтения и
  публикации до 20 мкс в целевом профиле Worms.
- `FIXED_SCHEDULE` работает без чтения быстрого счётчика во время игры.
  Приложение предоставляет кадровую эпоху и гарантированные точки вызова.
  Шлюз списывает из фиксированной квоты заранее проверенную верхнюю стоимость
  порции (§5.1). Для каждой точки профиль задаёт интервал с джиттером и
  доступное время до обязательного обслуживания звука или другого устройства.
  Если доказанного запаса нет, из этого обработчика допустим только короткий
  флаг. Длительности порций, DI и пауз между полезными опросами проверяются
  внешней трассой на тех же CPU, памяти и видеорежиме, включая границу кадра.

Оба способа соблюдают те же квоты и пределы карты. INIT проверяет гарантии
приложения до разрешения приёма. Если недоступна только своевременная проба
IRQ, используется POLL. Если невозможно обеспечить даже POLL или сроки STEP,
возвращается UNSUPPORTED_TIMING. Смена делителей, остановка часов либо смена
режима нагрузки, влияющая на эти гарантии, требует согласовать новый профиль
до продолжения сетевой работы. Адаптер может поддержать смену источника,
если сохраняет непрерывность времени и все заявленные пределы.

**Пример APP_COUNTER в Worms.** С разрешения игры шлюз читает существующую
цепь CTC2/CTC3. В текущей MAME входная частота 875 кГц, делители 112 и 156,
период фазы 17 472 отсчёта. Один отсчёт занимает около 1,143 мкс.
Читать CTC3 → CTC2 → CTC3. Если старшая фаза изменилась,
повторить не более одного раза. Второе несовпадение — «нет метки»: не допускать
непроверенную работу, учесть ошибку времени. [Существующее чтение фазы](https://github.com/witchcraft2001/worms/blob/3784e6d52962134fe09e8e89eb3242df4ff5c339/src/platform/ctcnow.inc)
служит образцом; игровую `time_now` с EI/DI и повтором нельзя вызывать из ISR.
Если владелец применяет другие делители или использует каналы для звука,
выбирается соответствующий адаптер или FIXED_SCHEDULE. При вычислении оборота
нужно учитывать, что обновление `ctc_ticks` может ещё ожидать под DI.

Фаза = (156 − CTC3) × 112 + (112 − CTC2), нормализована в 0…17 471;
дельта считается по модулю **17 472**, а не 65 536. Шлюз ведёт монотонный
32-битный счётчик отсчётов по дельтам; публикация атомарна, обновление от
таймера обязательно чаще одного оборота (для профиля — не реже 4 мс). При
неизвестном числе оборотов запрещено выдавать правдоподобную разницу: требуется
повторная синхронизация до допуска. Для длинных сроков используются настенные
`now_ms`, накапливая миллисекунды из дельт с дробным остатком, а не
переводя абсолютное значение уже обернувшегося 32-битного счётчика отсчётов.
Для коротких сроков используются разности отсчётов с учётом wrap. Отдельно ведётся
эпоха видеокадра: в модели кадр 17 920 отсчётов (20,48 мс), а не период CTC.
SDK калибрует обе шкалы на целевой плате. Чтение с повтором входит в стоимость
APP_COUNTER и проверяется при активном видео-DMA.

В текущем [Worms](https://github.com/witchcraft2001/worms/blob/3784e6d52962134fe09e8e89eb3242df4ff5c339/src/video_boot.asm) включён **беззвучный CBL без IRQ**:
фактической измеренной задержки звукового ISR игры ещё нет. Для квалификации
ввести явный звуковой профиль Worms: CBL mono 8 бит, rate 9, 10 937,5 выборок/с,
FIFO 256, событие пополнения на 128 выборок — каждые **11,703 мс**, а не с каждой
выборкой. Частота/размер взяты из режима River Raid (`src/sys/audio.asm`,
`CBL_HALF`); это расчётный период. Числовое требование стенда: от события до
начала пополнения ≤500 мкс (максимальное опоздание), до конца записи ≤1000 мкс,
ноль пропущенных пополнений. Это проектные пределы, которые проверяются под
нагрузкой на стенде. Для иной скорости/формата нужен свой паспорт периода,
джиттера и стоимости ISR; неизвестное значение не даёт права включать сеть
из CBL. В базовом профиле CBL только выставляет флаг после пополнения.

Срок опроса проверяется по меткам APP_COUNTER либо обеспечивается расписанием
FIXED_SCHEDULE независимо от срока следующего STEP. Неудачный try-lock не продлевает ни один срок. Если расчёт
WCET, частота опроса и квоты не позволяют одновременно выдержать сроки карты,
аудио и STEP, INIT_CONFIG возвращает UNSUPPORTED_TIMING до разрешения приёма.
Под нагрузкой сетевая карта может приостановить входящий поток либо учесть
потерю; ядро запрашивает MASK_ROUTE, только шлюз меняет PIO.

## 6. Требования к аппаратным профилям

### 6.1. ESP

Первый обязательный профиль — прошивка ESP-AT 2.2.2 с подтверждённым пассивным
приёмом TCP; эта возможность проверяется на поставляемом образе прошивки до
квалификации профиля. Активный поток UDP обслуживается отдельно. ESP-AT 2.2.1
не включается автоматически в тот же профиль: отсутствие CIPRECVMODE требует
отдельной квалификации.

UART TL16C550C имеет RX FIFO на 16 байт и таймаут неполного FIFO.
Начальный профиль — 115200 бод, 8N1, программное RX-кольцо 512 байт.
Первый кандидат для POLL с auto-RTS — порог 8, для сравнения испытать 4.
Данные в POLL читаются по LSR. Для IRQ сравнить пороги 8, 14 и 4.
Менять FCR при fallback без очистки FIFO и переключения enable/reset; если
клон этого не гарантирует, сохранять рабочий порог до безопасной настройки
вне соединения. Приём осушает FIFO за вход, **если помещается в квоту**;
иначе сохранить pending и приостановить поток. Цикл «до пустого FIFO» без
предела недопустим при непрерывном потоке.

При 115200 бод 8N1 передаются 11 520 байт/с. Без остановки передатчика пустой
FIFO заполнится за 1,39 мс. Для оценки насыщения, если каждый IRQ забирает ровно
байты порога и сразу приходит следующий пакет байтов:

| Порог | RX IRQ/с (расчёт) | Запас до заполнения после порога | Обвязка 30–60 мкс, на 20 мс |
|---|---:|---:|---:|
| 4 | 2880 | 1042 мкс | 1728–3456 мкс |
| 8 | 1440 | 694 мкс | 864–1728 мкс |
| 14 | ≈823 | 174 мкс | ≈494–987 мкс |

30–60 мкс — предположение для сравнения, не замер. Порог 14 сокращает число
IRQ, но у этого UART auto-RTS снимается лишь при начале **16-го** символа.
Публиковать для каждого режима расчёт насыщения, измеренные стоимость входа,
реакцию ESP на RTS, худший service gap и число переполнений. Выбирать порог
по этим данным; нельзя обещать полную скорость линии в игровом бюджете.
[TI TL16C550C, §§7.2, 7.7.3–7.7.4](https://www.ti.com/lit/ds/symlink/tl16c550c.pdf).

При насыщении в POLL с auto-RTS передатчик может останавливаться на каждом
опросе. Для порогов 4 и 8 рассмотрим установившийся цикл с полным осушением
FIFO каждые 2500 мкс. Скорость UART в этом расчёте равна числу считанных байт,
делённому на 0,0025 с. Число байтов в пути после снятия RTS зависит от модуля.

| Порог POLL | Без дополнительных байтов, байт/с | Ещё 1 байт, байт/с | Ещё 2 байта, байт/с |
|---:|---:|---:|---:|
| 4 | 1600 | 2000 | 2400 |
| 8 | 3200 | 3600 | 4000 |

Для полезных 2048 байт/с требуется в среднем 5,12 байта полезной нагрузки за
такой цикл, сверх них идут ответы и заголовки ESP. Таблица оценивает сырую
пропускную способность при заданных интервале и числе байтов. Квалификация
измеряет полезные данные в обоих направлениях одновременно. Проверить
пропущенный тик, занятость ISA, реальную реакцию на RTS, число байтов за опрос
и переполнения. В AUTO проверить тот же обмен с его более длинным интервалом
резервного опроса и при потере IRQ.

Обязательный ESP/POLL-профиль должен иметь проверенное управление потоком:
проводка RTS/CTS, настройки обоих UART и реальная реакция прошивки. Одного бита
AFE недостаточно как доказательства: в текущих исходниках ESP уже отмечены
проблемы burst-приёма с одним auto-RTS. Предусмотреть явную приостановку RX до
исчерпания программного буфера, запас на байты в пути и возобновление после
освобождения места. Проверить это и при бюджетном YIELD, и при занятой ISA.

Вариант без RTS/CTS допустим лишь как отдельно проверенный профиль с меньшей
скоростью либо гарантированным частым опросом. При отсутствии IRQ одновременно
с отсутствием flow control библиотека не обещает сохранность произвольного
потока. Пассивный TCP не отменяет приём уведомлений и ответов ESP через UART.
Скорость и управление потоком не меняются посреди сессии при переходе на POLL.

ISR обслуживает RX, таймаут неполного FIFO и ошибки UART; TX-empty IRQ разрешён
только при наличии ожидающих байтов. Когда TX пуст, этот IRQ отключается.
При переходе пусто → есть TX проверить LSR/THRE и начать запись непосредственно
при свободном THR либо оставить TX pending для таймера. Нельзя зависеть от
нового фронта ETBEI на уже пустом передатчике. После включения IRQ повторно
проверить состояние под тем же владельцем FIFO; отправка ровно один раз.
Все пути имеют предел порции/времени, даже если новые байты поступают постоянно.
Биты MCR OUT1/OUT2 нельзя использовать по PC-шаблону включения IRQ: на
SprinterESP они управляют RESET/PGM модуля.

UART overrun означает потерю целостности AT-потока: увеличить счётчик,
выдать ошибку, прекратить выдачу сомнительных данных и выполнить ограниченное
по времени восстановление; при невозможности — закрыть повреждённый канал
с явным событием. WIFI DISCONNECT и спонтанный ready также превращаются
в события потери связи/перезапуска, а не в зависшее ожидание.

### 6.2. RTL8019AS и 3C509B

Приём, передача, переполнение и завершение аппаратных операций определяются
по регистрам карты независимо от наличия IRQ. Настройка разрешённых причин IRQ
и их подтверждение специфичны для каждой карты; общим остаётся ABI обслуживания.
Нельзя использовать наличие только кадра/клавиатурного IRQ как доказательство
достаточной частоты опроса Ethernet-карты.

Профиль включает размер доступного аппаратного буфера, ограничения ISA,
порцию копирования, `max_service_gap_us` и допустимую игровую нагрузку.
При избытке чужого трафика разрешены учитываемые потери пакетов, но не выход
за бюджет CPU, зацикливание discard или повреждение состояния драйвера.
TCP восстанавливает потерянные сегменты; UDP не получает ложной гарантии
доставки. Каждая карта должна пройти TCP- и UDP-тесты в POLL отдельно.

## 7. Диагностика и пример SDK

Версионируемый `GET_INFO` сообщает возможности POLL/IRQ, требования к памяти,
минимальный бюджет, максимальную неделимую операцию, `poll_gap_us`,
`auto_fallback_gap_us`, `irq_delivery_us`, `max_service_gap_us` и независимо
`max_step_gap_ms`. Возможность IRQ для квалифицированного подключения и успех
пробы в этом сеансе — разные поля. `GET_STATS` сообщает фактический режим,
проверенность маршрута и причину fallback, число IRQ и опросов по источникам,
budget-yield, BUS_BUSY, максимальные время вызова/DI/паузу аппаратного обслуживания,
`max_observed_step_gap_ms` между результативными вызовами STEP на часах now_ms,
нарушения срока, UART overrun, переполнения колец, повторы TCP и раздельные
отбрасывания по размеру, checksum и чужому адресу. Снимок читается из main
без частично обновлённых многобайтных полей.

SDK должен включать пример смешанного обслуживания:

1. До игры: загрузка библиотеки, получение конфигурации и проверка таймингов.
   Подготовить кольца, источник now_ms, гарантированный вызов опроса и, если нужен, шлюз PIO/IM2
   с замаскированным источником. Только после этого разрешить приём и пробу.
2. Таймер: опрос по сроку; аппаратный IRQ: тот же STEP_ISR с другим source;
   кадр/клавиатура: дополнительные возможности; CBL: только pending-флаг.
3. Основной цикл: события и RX/TX-очереди, STEP из фиксированной квоты main.
4. Во время паузы продолжаются настенные часы, бюджетные периоды, опрос и TCP.
5. При выходе шлюз маскирует сетевой маршрут и вызывает SHUTDOWN из main.
   При WORK продолжает STEP и чтение событий, затем снова вызывает SHUTDOWN.
   Срок аппаратной остановки отсчитывается по now_ms первого STEP в STOPPING.
   Ядро отключает IRQ в карте и
   останавливает обмен, включая DMA соответствующего профиля. После OK шлюз
   восстанавливает PIO/IM2, тени портов и страницы. Загрузчик выполняет
   освобождение DLL с вызовом FINI и возвращает управление DSS.
   Порядок после аппаратного отказа и условия повторного INIT определяет §3 ABI.

Числовой пример SDK (целевые верхние оценки, не замер): таймер 2 мс,
квалифицируемые пределы `poll_gap_us=2500`, `auto_fallback_gap_us=5000`,
`irq_delivery_us=2000`,
`max_service_gap_us≥5000` **только для профиля с доказанной остановкой потока**.
В проверенном AUTO достаточно опроса на каждом втором тике, в POLL — на каждом.
Допуск лишь при подтверждённом суммарном джиттере; если BUS_BUSY грозит сроку,
обязателен ограниченный повтор в доступном окне или приостановка потока.
Пример не применяется к 115200 без управления потоком.

| Квота на физический кадр | Пример верхней оценки, включая шлюз |
|---|---:|
| Таймер и обязательный опрос | 1100 мкс: до 11 × 100 (до 60 тело + до 40 обвязка) |
| IRQ карты | 200 мкс: до 2 × 100, затем маскирование и опрос |
| STEP из main | 600 мкс: 2 × 300, разнести по времени для max_step_gap_ms |
| Прочие входы, учёт эпохи и аварийное маскирование | 100 мкс; обосновать верхний предел их числа и цены |
| **Всего** | **2000 мкс** |

В 20-мс окне с десятью тиками, двумя IRQ и двумя STEP первый IRQ получает
полную порцию 100 мкс, второй встречает занятую ISA до входа в ядро.
Если профиль подтвердит `busy_path_us = 65` мкс, дебет составит
1000 + 100 + 65 + 600 = 1765 мкс плюс до 100 мкс служебных расходов.
В IRQ-квоте останется 35 мкс, чего недостаточно даже для пути в 65 мкс.
Шлюз маскирует маршрут и откладывает следующий вход. При обычном полном
дебете за оба IRQ тот же пример потребует 1800 мкс плюс обвязку служебных
входов. В физическом кадре
20,48 мс возможны одиннадцать тиков: остаётся тот же потолок 2000 мкс.
Неиспользованный резерв нельзя отдать main. Пример должен пройти Z80-стенд
с реальной обвязкой; если 40 мкс на неё недостаточно, уменьшить полезную
порцию или пересчитать профиль, а не исключать обвязку из отчёта.

## 8. Проверки и критерии приёмки

### 8.1. Уровни приёмки и допустимые стенды

Каждая строка проверяется отдельно; успех одной карты или TCP не заменяет
остальные проверки. Loopback проверяет ABI, но не аппаратные ограничения.

| Профиль | POLL, IRQ отключён | AUTO, линия отсутствует | AUTO, рабочий маршрут | Потеря IRQ в обмене |
|---|---|---|---|---|
| ESP/TCP | Б: Z+M+Ж | Б: Z+M | И: M+Ж | И: Z+M |
| ESP/UDP | Б: Z+M+Ж | Б: Z+M | И: M+Ж | И: Z+M |
| RTL8019AS/TCP | Б: Z+M+Ж | Б: Z+M | И: M+Ж | И: Z+M |
| RTL8019AS/UDP | Б: Z+M+Ж | Б: Z+M | И: M+Ж | И: Z+M |
| 3C509B/TCP | Б: Z+M+Ж | Б: Z+M | И: M+Ж | И: Z+M |
| 3C509B/UDP | Б: Z+M+Ж | Б: Z+M | И: M+Ж | И: Z+M |

Б — обязательно для выпуска аппаратного профиля. И — обязательно **для
публикации поддержки конкретного IRQ-маршрута**, но не блокирует POLL-only.
Z — исполняемый Z80 с моделью устройств и инъекцией событий; M — MAME;
Ж — реальный Sprinter. Знак + требует оба/все указанные стенды. В графах И
нужен расширенный MAME с маршрутизацией. Для неподтверждённой разводки
обе графы И получают «маршрут не квалифицирован», а GET_INFO не объявляет IRQ.
Без проверки Б на железе возможен экспериментальный образ с явной отметкой,
но не аппаратно квалифицированный выпуск. Физический обрыв проводника на
работающем Sprinter не требуется: обрыв, пропуски и удержание вводятся на M/Z.

«Линия отсутствует» означает, что карта может формировать IRQ, но он не
доставляется PIO; это отдельный тест от программного отключения IRQ карты.
Проверить и AUTO без описания маршрута, и, при наличии кандидата с безопасной
пробой, AUTO с разрешённым, но не доставляемым сигналом.
Конкретные допустимые ISA-слоты, адреса, конфигурации IRQ, скорости и flow
control перечисляются в отчёте; неизвестная разводка проверяется как POLL.

### 8.2. Функциональные и отказные сценарии

- В каждом режиме: инициализация, подключение, двусторонний обмен, чат,
  простой, пауза игры, закрытие и повторное подключение. Без IRQ всё работает
  при отсутствии клавиатурных событий и CBL; нужны гарантированный опрос
  приложением и STEP в основном цикле с соблюдением обоих независимых сроков.
- Не менее 30 минут обмена для каждой аппаратной сборки в POLL и AUTO без
  линии IRQ: последовательные номера, длины и контрольные суммы на уровне
  стенда. Проверять ARP после истечения записи соседа и переход счётчика now_ms
  через ноль; время можно ускорять в отдельном модельном тесте.
- Базовая нагрузка: полезные 2 КиБ/с в каждом направлении, включая служебные
  сообщения приложения, плюс серии коротких сообщений и согласованные burst.
  Для UDP учитывать доставку отдельно; в чистом стендовом канале внутри
  заявленной нагрузки аппаратные переполнения и потери из-за опроса недопустимы.
- Отключение линии посреди RX/TX, отдельные потерянные IRQ, задержанный IRQ,
  удерживаемый уровень, IRQ после маскирования и событие при повторном
  разрешении. Fallback сохраняет порядок, очереди и соединение; обработчик
  не зависает и не создаёт IRQ storm. Тихий канал не вызывает ложный fallback.
- Раздельно проверить A для обслуживания данных, D + A для причины с меткой
  и 2 × A для двух последовательных находок при нагрузке. Между находками
  внедрить также исправный IRQ и пустой опрос, проверить сброс последовательности.
- Одновременные таймер, кадр, клавиатура, CBL и IRQ карты; повторный вход
  во время STEP; занятая ISA; исчерпание бюджета перед IRQ; задержанный main;
  пропуск кадра и возврат вызова после смены бюджетного периода. Нет двойного
  расходования или ошибочного пополнения квоты, повторного чтения байта,
  потери индексов кольца и ожидания внутри ISR.
- В тесте со звуком, занявшим ISA до входа в SDK, проверить дебет только
  квоты источника. При нехватке квоты источника проверить дебет только
  служебной квоты. При успешном захвате шлюзом трасса показывает один захват
  и одно освобождение шлюзом на каждом выходе ядра. Отдельно дать ядру порцию
  без предзахвата, занять ISA перед поздним обращением к ней и проверить
  BUS_BUSY с полным дебетом. Повторить на границе кадра.
- ESP: уведомление короче порога FIFO, разрыв +IPD после каждого байта,
  RX/TX одновременно, заполненный программный буфер, задержка реакции на RTS,
  остановленный CTS, UART overrun, перезапуск ESP и потеря Wi-Fi. Проверить
  постановку TX при пустом THR и включении ETBEI без нового фронта, единичную
  передачу и возобновление таймером; смешанные уведомления и короткий/нулевой
  ответ CIPRECVDATA со строкой «CLOSED» внутри двоичных данных (см. ABI).
  Проверить принудительный POLL и fallback с каждым поддержанным baud/flow-профилем;
  небезопасный профиль отклоняется явно до обмена.
- Ethernet: постоянный чужой трафик, плохие checksum, полное RX-кольцо,
  незавершённый discard, TX timeout; всё в POLL и AUTO. В TCP проверить также
  односторонний поток с delayed ACK и zero-window без блокирующего ожидания.
- Второй Sega через LPT, прочие используемые ISA-устройства, восстановление
  #1FFD/#9FBD и возврат в DSS после нормального выхода и ошибки сети.
- SHUTDOWN без канала, с занятыми TX/RX, после частичного INIT и после
  фатального отказа. Проверить полный буфер событий, занятую ISA, активный DMA,
  таймаут остановки, повтор SHUTDOWN и INIT после OK. До снятия вектора
  карта должна прекратить IRQ и доступ к буферам. Метки TX завершаются один раз.
  Разнести последний STEP до остановки и первый STEP в STOPPING по времени.
  Проверить дедлайн от второго из этих вызовов, в том числе при BUS_BUSY,
  повторном SHUTDOWN и переходе now_ms через ноль.
- RX_READY при поступлении данных во время осушения RX, при заполненной
  очереди событий и при новом переходе после RX_RELEASE последнего слота.
  Для отказа OPEN проверить графики ARP/SYN с общим дедлайном, разрешение
  ARP непосредственно перед дедлайном и последовательность TIMEOUT(OPEN), CLOSED.
- Для DE проверить просроченный срок, 0xFFFE, более дальний срок и отсутствие
  срока. По трассе сверить `max_observed_step_gap_ms` при паузе, wrap и серии
  бюджетных отказов. Проверить константы статусов, источников и событий всех сборок.
- По векторам ABI: укороченный commit на последнем слоте, полные очереди,
  CANCEL для каждого незавершённого тега, RX до CLOSED, повтор CLOSE/ABORT,
  CONFIG_EXPIRED, таймауты повтора и проверки живости при тишине, маленький
  стек и буфер на границе окна. Проверить модульный переход фазы CTC,
  пропущенную эпоху, конфликт измерителя с CTC IRQ и отказ невалидных часов.
- Запустить обмен, когда все каналы CTC заняты игрой. В FIXED_SCHEDULE трасса
  ядра и сетевого шлюза должна показать ноль обращений к портам CTC от INIT
  до выхода, включая ошибки. У игры сохраняются её векторы, частота тика и
  работа звука. Повторить в APP_COUNTER с независимой шкалой, а с разрешённым
  CTC-адаптером проверить отсутствие записей. В обоих режимах проверить
  паузу и fallback при потере IRQ. Слишком редкие вызовы должны приводить
  к UNSUPPORTED_TIMING до включения приёма. Значения, недоступные для измерения
  во время исполнения, в GET_STATS отмечаются как недоступные.

### 8.3. Время, задержки и доказательства

Для всех шести сборок автоматические тесты исполняют Z80-код со скриптованными
UART/NIC-событиями и проверяют порционность, возобновление и верхние границы
операций. Проверки размера и запрета DSS/BIOS/libman действуют с первого входа.
Для каждого из семи файлов проверить сигнатуру L1 и выполнить
`sprinter-mkdll verify <файл.DLL> --target 1.3`. На стенде со штатным
libman проверить загрузку через `l_load`, заголовок через `l_info` и
освобождение через `l_free`. Сверить релокацию и адреса игровых входов
с результатом загрузки SDK. Трасса запрета DSS относится к коду библиотеки
и вызовам во время игры. Подготовка и выгрузка выполняются вне игрового цикла.
Модель T-state служит регрессией, но не заменяет измерение реальных ISA-ожиданий.

На Sprinter измерять при включённом турбо, активном видео-DMA, работе звука
и ввода; фиксировать плату, игровую конфигурацию, карту, прошивку, частоты,
режим IRQ/POLL, нагрузку и метод калибровки. Отдельно измерять весь сетевой
бюджет за кадр, время STEP/STEP_ISR, непрерывный DI, максимальный service gap,
задержку CBL, пропущенные предъявления и UART/кольцевые переполнения.

На контролируемом стенде целевой срок TX_COMMIT → начало аппаратной передачи
и готовые данные карты → публикация RX — не более 40 мс при нормальной игровой
нагрузке и работающем peer. Условия: нет zero-window/CTS-блокировки, потерь
сети и очереди сверх заявленной нагрузки. Для ESP измеряются отдельно UART,
приём модулем и наблюдение у peer; SEND OK не считается доказательством
передачи в эфир или получения сервером. Вне этих условий сохраняются
бюджеты CPU и явные таймауты, а не обещание задержки доставки.

Нагрузочный прогон интеграции: 30 000 аппаратных кадров на сборку в POLL
и AUTO без IRQ, с видео и звуком. Приёмка требует общего сетевого времени
≤2 мс/кадр, соблюдения допустимого service gap и срока аудио, отсутствия
потерь кадров по вине сети, зависших состояний и UART overrun в заявленном
профиле. Все IRQ-входы и дополнительные флаги CBL входят в измерение.
Интервал 30 000 кадров разрешено выделить внутри того же 30-минутного
прогона при идентичной нагрузке: 6 профилей × 2 режима = 12 прогонов
(6 часов времени стенда при скорости 1×). Протокол содержит обе группы метрик.

Текущая проверенная модель Sprinter в MAME не соединяет IRQ ISA со входами
PIO: это позволяет проверять fallback, но не подтверждает аппаратный IRQ.
Для IRQ-тестов сначала дополнить модель маршрутизацией и управляемыми
отказами линии. Результаты модели, MAME и реального Sprinter вести отдельно;
незапущенные аппаратные сценарии отмечать «не проверено», а не «пройдено».

### 8.4. Порядок работ и риск стенда

1. На нулевой вехе измерить стоимость адаптера времени приложения (для
   CTC-варианта Worms — чтение фазы), обвязку/DI, CBL и стоимость ISA,
   зафиксировать ABI/include и подтвердить размер 3C509B/TCP прототипом.
2. Квалифицировать POLL и AUTO без линии для каждой сборки независимо от
   готовности IRQ-эмуляции. Один общий сценарий запускается с шестью профилями.
3. Отдельная работа для MAME: подключить IRQ двух групп слотов к PIO, не сломать
   LPT; добавить управляемые отключение, запаздывание, пропуск и удержание
   сигнала, затем регрессии на UART и обеих NIC. Плановая оценка **3–6
   инженерных дней** при работоспособных моделях карт; пересмотреть после
   первого сквозного сигнала. Ремонт самой модели NIC оценивается отдельно.
4. Закрывать графы И по одному проверенному маршруту. Отчёты Z/M/Ж содержат
   версию стенда, разводку, конфигурацию, ожидаемые и фактические результаты.

## 9. Поставка и источники аппаратных требований

Поставка: шесть библиотек и loopback, [нормативный ABI v1](unet-game-abi.md)
и согласованный с ним общий include, загрузчик и шлюз SDK,
примеры POLL/AUTO со смешанными ISR, тесты, таблица поддержанных подключений,
размеров и таймингов, отчёт по матрице приёмки. Игра и библиотеки не должны
требовать переделки платы ради подключения IRQ.

### 9.1. Имена библиотек UNET-GAME

Игровые библиотеки v1 именуются по схеме `G<протокол><тег карты>.DLL`.
После префикса игрового ABI `G` идёт `TCP` или `UDP`, затем тег карты.
Расширение `.DLL` и формат файла соответствуют libman. Загрузчик игрового SDK выбирает
из своего манифеста точное имя для пары «карта, транспорт». Для DSS-библиотек
старого ABI действует отдельное правило UNETLD `UNET<тег>.DLL`.

| Карта | Образ TCP | Образ UDP |
|---|---|---|
| SprinterESP | `GTCPESP.DLL` | `GUDPESP.DLL` |
| RTL8019AS | `GTCPRTL.DLL` | `GUDPRTL.DLL` |
| 3C509B | `GTCP509B.DLL` | `GUDP509B.DLL` |

Седьмой образ, общий loopback, поставляется как `GLOOP.DLL`.
Для всех семи файлов используется DOS 8.3, заглавные ASCII-буквы и цифры,
одна точка и одинаковое имя в архиве и на диске. Имена стабильны для
совместимых выпусков v1. Версию проверяют по ABI. Выбор POLL или AUTO
выполняется в INIT_CONFIG и использует один файл профиля.

Общий include SDK для sjasmplus поставляется как `UNETGAME.INC`. В нём
публичные имена игрового ABI получают префикс `UNETG_`. Например, экспорт
STEP доступен как `UNETG_STEP`, статус BUS_BUSY как `UNETG_STATUS_BUS_BUSY`,
источник CARD_IRQ как `UNETG_SRC_CARD_IRQ`. Краткие имена в тексте ABI
обозначают те же операции и значения.

На этапе сборки сверять имена из манифеста SDK с этой таблицей и с содержимым
архива и образа диска. Проверять уникальность всех семи базовых имён без
учёта регистра и их отличие от базовых имён DLL старого ABI.

### 9.2. Источники

Формат DLL и поведение загрузчика определены в репозитории `sources/libman`,
в разделах «Форматы L0, L1 и L2» файла `README.md` и «API и диагностика» файла
`libman/README.md`. Образцы существующих L1 находятся в
`sources/unet_libs/unet_libs_core/dll`.

Аппаратные основания, проверенные при подготовке требований:

- [SprinterESP v1.0.5, схема](https://zxgit.org/romych/SprinterESP/src/branch/master/Export/Schematic_Sprinter-ESP_v1.0.5.png): INTR → ISA IRQ3, назначение RESET/PGM.
- Руководство Sprinter 2000, `board/sp2000.pdf`, §9.3, стр. 25: ISA IRQ через
  PIO B; схема SP-DX `board/spdx_release_v306_25.05.2025/docs/sp-dx-sch.pdf`,
  лист ISA, и адаптер `board/ext-cpu-isa`: маршруты групп слотов.
- [TI TL16C550C](https://www.ti.com/lit/ds/symlink/tl16c550c.pdf): FIFO,
  пороги, RX timeout, управление потоком и причины IRQ.
- Локальная модель `mame/src/mame/sinclair/sprinter.cpp`: конфигурация ISA
  и PIO; наличие эмулируемой карты само по себе не означает подключения IRQ.
- `sprinter_wifi/network/src/lib/tput_lib.asm` и `esplib.asm`: ограничения
  AFE в burst-режиме и необходимость проверять полный профиль приостановки RX.
- [Ввод Worms](https://github.com/witchcraft2001/worms/blob/3784e6d52962134fe09e8e89eb3242df4ff5c339/src/input.asm): использование PIO B вторым Sega через LPT.

Пути к аппаратным материалам и соседним проектам приведены относительно
каталога Sprinter; они не являются зависимостями сборки Worms. Факты разводки
и документация компонентов не считаются результатом теста новой библиотеки.
