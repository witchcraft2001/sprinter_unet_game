Графа Z для карт означает POLL на стенде с моделью карты и собеседником.
Графа M для ESP — POLL в MAME holub с картой `sprinter_esp` и эмуляцией
ESP-AT 2.2.0.0 (`docs/TESTING.md`). Графа M для карт Ethernet — NETDEMO в
MAME: RTL8019AS (`rtl8019as`, holub) и 3C509B (`3c509b`, сборка MAME
разработчика); обмен идёт через pcap на паре feth. Прогон 31.10.2026:
56 из 56 сценариев `make test-m` пройдены (`docs/evidence/m3_eth/`).
Шаг STEP — 2 мс виртуального времени, как обещает конфигурация
`worst_poll_gap_us = 2000`; потоковые сценарии и `make profile-check`
повторяются при шаге 10 и 20 мс. Каждый вызов проверяется на бюджет, DI ≤ 200 мкс,
стек, дисциплину ISA и точное восстановление `#1FFD/#9FBD/#E2`. Собеседник
проверяет контрольные суммы IP/TCP/UDP каждого кадра от DLL. Модельный прогон
не доказывает реальных таймингов ISA и маршрутизации IRQ.

## Loopback (GLOOP), стенд Z

- **ABI.** Векторы ABI §2–§5 пройдены (`tests/z/abi/m1_queues.test.js`): очереди,
  события, ABORT, CLOSE, SHUTDOWN, CONFIG_EXPIRED на переходе через ноль,
  сроки в DE, `max_observed_step_gap_ms`.
- **Общие векторы.** На всех семи сборках пройдены INIT/FINI, GET_INFO,
  INIT_CONFIG с BAD_CONFIG и UNSUPPORTED_TIMING (`tests/z/abi/m0_init.test.js`).
  Это проверка ABI, а не аппаратных ограничений.
- **Бюджет.** Перебор бюджетов от опубликованного минимума 380 мкс до 500 мкс
  даёт 0 превышений, и при минимуме данные идут.

соединение и эхо, минимальный бюджет, поток 8 КиБ, STEP_ISR и BUS_BUSY.

## Сценарии карт, стенд Z

**RTL8019AS** (`tests/z/hw/rtl/m2_rtl.test.js`, модель `tools/harness/devices/rtl8019.js`):

- программирование DP8390 для 8-битного опроса и MAC из PROM;
- удвоенная раскладка PROM;
- пустой слот приводит к FAULT без ожидания;
- кадры без сохранённой FCS;
- переполнение кольца, сброс кольца и продолжение обмена;
- ошибка передачи: UDP получает TX_DONE FAILED, TCP повторяет;
- зависший передатчик: сброс и возобновление;
- потерянный RDC: кадр не запускается.

**3C509B** (`tests/z/hw/el3/m3_el3.test.js`, модель `tools/harness/devices/el3.js`):

- MAC из EEPROM;
- ожидание CIP как состояния.

**SprinterESP** (`tests/z/hw/esp/m4_esp.test.js`, модель `tools/harness/devices/esp.js`),
обе сборки, если не указано иное:

- UART программируется один раз: IER 0, 8N1, делитель 8, один сброс FIFO до
  auto flow, MCR = AFE|RTS, линии RESET/PGM модуля не трогаются;
- точная последовательность настройки модуля;
- пустой слот даёт FAULT без ожидания; триггер FIFO из INIT_CONFIG;
- ESP-AT 2.2.1: TCP — FAULT (нет пассивного приёма), UDP работает;
- `busy p...`: команда повторяется;
- отказ соединения: PEER_CLOSED, затем CLOSED, без CONNECTED;
- `SEND FAIL`: TX_DONE FAILED только этого слота;
- нагрузка с `CLOSED`, `OK`, `+IPD,`, `ready`, NUL — данные;
- закрытие собеседником: PEER_CLOSED, затем CLOSED;
- перезапуск модуля: LINK_LOST, CLOSED, повторная настройка, новый OPEN;
- `WIFI DISCONNECT`: LINK_LOST, затем CLOSED;
- переполнение UART: STREAM_ERROR(UART_OVERRUN), счётчики, новый OPEN;
- закрытие во время CIPSEND: нагрузка уходит целиком, затем CIPCLOSE;
- потерянный ответ на CIPSEND: TIMEOUT(TX), модуль настраивается заново;
- TCP: ответ, приходящий по байту; короткие и пустые ответы CIPRECVDATA
  без FIN и без немедленных повторов; полное кольцо RX останавливает
  чтение, данные ждут в модуле;
- UDP: датаграмма длиннее слота и датаграмма без свободного слота
  отброшены и учтены; отставание парсера снимает RTS явно, без переполнения.

## Не проверено

- **Сценарии §8.2.** Не запускались:
  - 30-минутный прогон;
  - переход `now_ms` через ноль на картах;
  - истечение записи ARP;
  - zero-window;
  - полное RX-кольцо приложения;
  - незавершённый discard;
  - SHUTDOWN с активным DMA.
- **AUTO и IRQ.** Режим AUTO без линии и все графы И не проверялись; ядро
  обслуживает AUTO через POLL и не реализует пробу IRQ.
- **SDK на железе.** NETDEMO на реальном Sprinter не запускался.
- **MAME, карты Ethernet.** UGTEST E/S/P/D и NETDEMO H/L/E/S/P/D/W пройдены на
  всех четырёх сборках через pcap на паре feth (01.11.2026, после этапа
  квоты). STEP в MAME длится 0,68–0,93 мс в среднем и до 1,3 мс, как у
  сборок ESP (ожидания памяти MAME); это не замер бюджета. Сборки
  ESP проверены на эмуляции ESP-AT 2.2.0.0 (holub), а не на ESP-AT 2.2.2.
- **Железо.** Прогоны на реальном Sprinter не выполнялись ни для одной
  сборки. Пассивный приём ESP-AT 2.2.2 на настоящем модуле не проверен;
  соседние драйверы его тоже не проверяли на железе.
- **ESP-AT 2.2.1.** Не квалифицирована для TCP: без CIPRECVMODE настройка
  модуля кончается FAULT. На модели Z это проверено (TCP — FAULT, UDP
  работает); на настоящей прошивке не проверялось.
- **Цели ТЗ по скорости, выполненные частично.** Пустой опрос (55 мкс
  опубликовано, норма ≤100), BUS_BUSY (25, норма ≤25) и сумма квот профиля
  SDK по умолчанию (1970–2000 мкс при норме 2000) выполнены на стенде Z
  (`tests/z/abi/perf_targets.test.js`, `tests/z/sdk`). Пропускная
  способность ESP (ТЗ §6.1, 2048 Б/с полезных данных в каждую сторону,
  стенд Z, шаг 2 мс, бюджет 500) — **GUDPESP пройдено** (2,62 КиБ/с с
  поднятым бюджетом STEP_ISR, `UGP_ISR_BUDGET` 120–150, docs/SDK.md;
  1,49 на профиле SDK по умолчанию); **GTCPESP не выполнено** (1,22 на
  профиле по умолчанию, 1,95 (1996 Б/с) с поднятым бюджетом ISR — пассивное чтение
  TCP ждёт `CIPRECVDATA`, которую выдаёт только main-STEP, второй дренаж
  STEP_ISR не успевает набрать байты). Тест `tests/z/hw/eth_scenarios.js`
  держит цель видимой (`todo` у GTCPESP, обычный assert у остальных пяти
  сборок с картой, включая GUDPESP). Ж (реальное железо) — не проверено
  ни для одной ESP-сборки: ни порог автопотока RTS по умолчанию (8), ни
  поведение TL16C550C при двух читателях FIFO (main и STEP_ISR).
  Подробности в `docs/MEASUREMENTS.md`, «Этап ESP 2 КиБ/с».
