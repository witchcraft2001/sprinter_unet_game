# UNET-GAME — нормативный контракт ABI v1

Приложение к [ТЗ UNET-GAME](unet-game-spec.md). Контракт одинаков для шести
аппаратных профилей и loopback. Файлы используют формат DLL L1 для libman 1.3,
как существующие UNET DLL. Игровые вызовы определяет настоящий ABI. На нулевой вехе мейнтейнеры
публикуют общий include: порядок и регистры входов/выходов, смещения полей и
флаги. Они проверяются одним набором вызывающих Z80-программ на всех сборках;
нельзя менять их отдельно в одном драйвере.
Имена файлов поставки, общего include и префикс публичных символов определены
в [§9.1 ТЗ](unet-game-spec.md#91-имена-библиотек-unet-game).

В таблице переходов L1 вход 0 зарезервирован для INIT при загрузке,
вход 1 — для FINI при освобождении. Игровые экспорты, включая INIT_CONFIG и
SHUTDOWN, занимают отдельные номера начиная с 2. Адрес перехода с номером N
равен `база загруженного образа + 0x20 + 3 × N`. База определяется после
релокации для выбранного окна. Handle, возвращаемый libman, обозначает
ресурс загрузчика и не является адресом перехода.

INIT выполняет ограниченную подготовку DLL и возвращает результат по правилам
libman. Настройку сети приложение запускает через INIT_CONFIG. Перед выгрузкой
активного контекста шлюз доводит SHUTDOWN до OK, затем загрузчик вызывает FINI.
FINI корректно завершается и при загрузке с последующим освобождением без
INIT_CONFIG. Прямые игровые вызовы сохраняют эту последовательность.

## 1. Конфигурация, память и владение шиной

Блоки INIT_CONFIG, GET_INFO и GET_STATS начинаются с версии ABI и размера
(два u16 little-endian). Версия равна `(major << 8) | minor`, для v1.0 это
0x0100 (байты 00 01). Размер проверяется до обращения к полям; неизвестная
major-версия или короткий обязательный префикс — BAD_CONFIG без настройки
карты. Дополнительный хвост той же версии пропускается. Все локальные числа,
включая порты TCP/UDP в конфигурации, little-endian; IPv4 — четыре октета в
сетевом порядке. В сетевом пакете многобайтные поля имеют сетевой порядок.

INIT_CONFIG передаёт профиль/транспорт, адреса и порт партнёра, локальные
IP/маску/шлюз, явный признак и срок действия конфигурации, режим POLL/AUTO,
квалифицированный маршрут либо «нет маршрута», параметры UART, сроки §4,
описание областей памяти, `isa_lock_ptr`, указатели на тени `#1FFD/#9FBD`
и гарантии планировщика. Шлюз сопоставляет эти гарантии с GET_INFO до разрешения
приёма. Для write-only порта действительную общую тень предоставляет владелец
платформы; неизвестное состояние нельзя заменить «обычным» значением.

Все указатели Z80 16-битные. До изменения карты проверить каждый полуинтервал
[адрес, адрес + длина) с расширенной арифметикой: переполнение 16 бит,
пересечение занятых областей, окна ISA или сменной страницы кода — BAD_CONFIG.
Проверять контекст, RX/TX-слоты, аппаратные кольца, события, флаг и тени ISA,
шлюз/IM2 и рабочий диапазон SP (в том числе адрес возврата). Например, при ISA
в WIN3 недопустим буфер, начинающийся ниже 0xC000, но пересекающий эту границу.
Выбранные страницы должны оставаться доступными с тем же содержимым из main
и ISR. Нельзя отображать код поверх исполняющегося шлюза или его стека.

Ядро не подменяет SP. Отдельно публикуются максимумы стека main и STEP_ISR
по всем ветвям, включая ошибки. Нормы v1: ≤256 байт основного вызова и ≤96
байт самого STEP_ISR; ещё ≤64 для входа CPU, шлюза и возврата из сетевого
ISR. Если сеть может прервать основной вызов на том же стеке, приложение
оставляет дополнительно к своему использованию не менее 256 + 160 = 416 байт
и учитывает стек других разрешённых ISR. Проверка — защитные байты и максимумы
на Z80. Вложенные прерывания внутри сетевого ISR запрещены.

**Общий try-lock ISA:** один инициализированный SDK байт в постоянной RAM,
адрес передан через `isa_lock_ptr`: 0 — свободен, 1 — сеть/main, 2 — сеть/ISR,
3 — звук, 4 — контроллер, 5…254 — зарегистрированные владельцы, 255 запрещён.
Все пользователи ISA обязаны использовать именно его; наличие отдельного
внутреннего замка драйвера его не заменяет. Проверка нуля и установка владельца
выполняются под одним коротким DI, затем восстанавливается допустимое состояние
IFF вызывающего. В ISR EI запрещён. Ненулевой байт, в том числе собственный
ID, означает BUS_BUSY без изменения портов. Владелец снимает захват только
после восстановления картирования и теней. При временном отображении ISA
шлюз гарантирует видимость кода/стека прерываемых обработчиков либо держит
короткую операцию под DI в пределах профиля. Каждый владелец декларирует
максимальное время удержания; незарегистрированный блокирующий драйвер
несовместим с гарантией `max_service_gap_us`.

Когда шлюз сам захватил ISA при допуске, он передаёт текущему вызову явный
признак предзахвата. Ядро пользуется шиной без повторного try-lock, возвращает
временное картирование и тени, затем шлюз освобождает свой захват на любом
выходе. Признак локален для этой порции. Совпадение ID владельца в общем
байте не даёт другому вызову права воспользоваться захватом. В порции без
предзахвата ядро само берёт и освобождает замок там, где ему требуется ISA.
Если шина занята при таком позднем обращении, исход BUS_BUSY сохраняет полный
дебет уже допущенной порции.

**Контракт допуска вызовов.** Алгоритм фиксированных квот и числовой пример
в §§5, 7 [основного ТЗ](unet-game-spec.md) обязательны для шлюза ABI v1:
до входа шлюз списывает квалифицированную стоимость выбранного пути. Если
try-lock отказал до входа в ядро из-за занятой шины, стоимость занятого пути
списывается из квоты источника (квалифицированный `busy_path_us` либо полная
стоимость по §5.1 ТЗ). Если остатка квоты источника недостаточно для выбранного
пути, шлюз оплачивает отказ в допуске только из служебной квоты.
После допуска полной порции её стоимость списывается
целиком при любом исходе. В ядро передаётся бюджет **тела** за вычетом обвязки.
Значение меньше стоимости входа не передаётся. STEP возвращает в DE значение
0 для наступившего срока, `min(оставшиеся_мс, 0xFFFE)` для будущего и
0xFFFF только при отсутствии протокольного срока. STEP_ISR не принимает
now_ms; отдельный флаг MASK_ROUTE независим от статуса BUS_BUSY/YIELD и не даёт
ядру права писать PIO. Диагностическое измерение не выдаёт дополнительной квоты.

### Коды результата и источника

Нормативные однобайтовые статусы возврата общие для всех сборок. Поле
`status` события TX_DONE имеет отдельную кодировку из §3.

| Код | Статус | Условие |
|---:|---|---|
| 0x00 | OK | Операция принята либо синхронно завершена по контракту входа |
| 0x01 | WORK | Есть продолжение, дать следующую порцию |
| 0x02 | YIELD | Доступное время исчерпано |
| 0x03 | IDLE | Сейчас нет работы |
| 0x04 | BUS_BUSY | Нужная порция ISA отложена из-за занятой шины |
| 0x05 | WOULD_BLOCK | Операция сейчас не помещается в очередь или слот |
| 0x06 | STATE | Операция недопустима в текущем состоянии |
| 0x07 | EMPTY | RX_PEEK либо NEXT_EVENT не нашёл элемента |
| 0x08 | BAD_CONFIG | Недопустим блок конфигурации, память или версия |
| 0x09 | UNSUPPORTED_TIMING | Профиль не укладывается в гарантии платформы |
| 0x0A | BAD_ARGUMENT | Недопустимые длина, номер слота, tag или source |
| 0x0B | DEVICE_FAULT | Аппаратная операция завершилась ошибкой |

В отдельном байте флагов STEP/STEP_ISR бит 0 (0x01) — MASK_ROUTE. Остальные
биты возвращаются нулевыми. Неуказанные коды статуса зарезервированы.
Шлюз обрабатывает флаг и при BUS_BUSY или YIELD.
Источники STEP_ISR кодируются полем `source:u8`.

| Код | source | Источник |
|---:|---|---|
| 0x01 | CARD_IRQ | IRQ сетевой карты |
| 0x02 | TIMER | Периодический обработчик приложения |
| 0x03 | FRAME | Кадровое прерывание |
| 0x04 | KEY | Прерывание клавиатуры |
| 0x05 | CBL | Звуковой обработчик с квалифицированной порцией |
| 0x06 | OTHER_IRQ | Иной зарегистрированный источник |

Остальные значения зарезервированы. Работа из основного цикла выполняется
через STEP. Выставление CBL-флага без вызова ядра не создаёт вход STEP_ISR.

## 2. Транспорт и память очередей

| Параметр v1 | Собственный стек Ethernet | SprinterESP |
|---|---|---|
| TCP | Локальный MSS 536, исходящий сегмент не больше согласованного MSS и доступного окна. До двух неподтверждённых сегментов, без задержки Nagle | До двух ожидающих передачи порций по ≤536 байт на стороне Z80; MSS, TCP-повторы и число сегментов на проводе принадлежат прошивке |
| UDP | До 512 байт полезных данных, фиксированный партнёр | Те же границы датаграммы и фильтрация доступными средствами квалифицированной прошивки |
| IPv4-фрагменты | Нет фрагментации TX и сборки RX: MF либо ненулевое смещение → discard со счётчиком | IP-заголовки на Z80 не видны; лимит применяется к полученным от модуля данным, внутреннюю сборку прошивки контролировать нельзя |

Для TCP предел двух сегментов не отменяет ограничений окна получателя, управления
перегрузкой и меньшего MSS партнёра. На ESP немедленно ставится передача, но
свойства TCP внутри модуля не объявляются возможностями Z80.
[TCP: RFC 9293, §§3.7.1, 3.7.4](https://www.rfc-editor.org/rfc/rfc9293.html).

Типовой профиль выделяет четыре слота TX и четыре RX. Полезная память слотов:
TCP 8 × 536 = **4288 байт**, UDP 8 × 512 = **4096 байт** (это альтернативные
сборки). Сверх этого GET_INFO указывает байты контекста, метаданных, событий,
аппаратных колец, стека и любых рабочих буферов; ESP отдельно учитывает RX на
512 байт. Одна и та же полезная область не может одновременно принадлежать
приложению и драйверу.

Очередь событий вмещает не менее `число_TX_слотов + 4` **полезных** записей.
При четырёх TX это восемь событий по 8 байт. Сторожевой слот кольца, если он
нужен, выделяется дополнительно. GET_INFO публикует ёмкость и требуемую память.

- TX_RESERVE(n), 1 ≤ n ≤ предел транспорта, возвращает один **непрерывный**
  участок и номер слота либо WOULD_BLOCK. Даже на последней позиции кольца
  буфер не делится: следующий слот снова первый. Свободный слот не означает
  возможность перезаписать ещё занятый. Повторная резервация при одной
  незавершённой резервации приложения — STATE.
- TX_COMMIT(slot, used, tag) допускает 1 ≤ used ≤ n; передаются ровно used
  байт, остаток никому не публикуется. При ошибке длины резервация сохраняется.
  Для отказа до commit служит TX_UNRESERVE(slot), без передачи/события.
  После commit приложение не пишет в буфер. Tag — u16 приложения, уникальный
  среди незавершённых операций и непрочитанных TX_DONE; 0xFFFF зарезервирован
  для резервации без commit.
- TX_DONE освобождает слот ровно один раз (номер + tag). Событие означает,
  что библиотеке больше не нужен буфер; оно не подтверждает обработку команды
  сервером. В частности, ESP SEND OK не является ACK партнёра. Потерянное
  подтверждение AT нельзя лечить слепой повторной отправкой полезных данных.
- RX_PEEK возвращает следующий неизменяемый участок, его длину и слот;
  повтор до RX_RELEASE даёт тот же участок. RX_RELEASE освобождает его целиком.
  Граница TCP-участка не является границей игрового сообщения. Полный RX TCP
  уменьшает объявляемое окно до нуля; освобождение места планирует обновление
  окна. ESP в пассивном TCP прекращает запрашивать данные, если места нет.
  UDP принимает одну датаграмму в один слот; при переполнении/превышении 512
  отбрасывает **всю** датаграмму и увеличивает соответствующий счётчик. Пустая
  входящая UDP-датаграмма — занятый слот длины 0, не признак конца TCP.

## 3. Состояния, события, завершение

OPEN из CLOSED с действующей конфигурацией ставит операцию в очередь; повтор
из OPENING/OPEN/CLOSING даёт STATE. Единовременно активен один канал (номер 0).
После успешного OPEN публикуется CONNECTED, для UDP это выбор партнёра, а не
рукопожатие. CLOSE инициирует завершение: запрещает новые TX, ограниченно
завершает прежние, затем CLOSED. CLOSE в CLOSING/CLOSED идемпотентен.
FIN партнёра означает полное закрытие; half-close в v1 отсутствует.
При асинхронном отказе принятого OPEN переход из OPENING отдаёт одну причину
(например, TIMEOUT с detail=OPEN), затем ровно один CLOSED. CONNECTED в этой
последовательности отсутствует. Синхронно отклонённый OPEN возвращает статус
без событий. Новый OPEN разрешён после получения CLOSED для принятой попытки.

Формат события — 8 байт: `type:u8, channel:u8, tag:u16, status:u8, slot:u8,
detail:u16`. Без слота slot=0xFF, без тега tag=0xFFFF, без detail — 0.
Для общего события channel=0xFF. NEXT_EVENT снимает одно событие в порядке
публикации либо сообщает EMPTY. Таблица типов нормативна:

| type | Событие | Значение |
|---:|---|---|
| 1 | CONNECTED | Канал открыт |
| 2 | RX_READY | Уведомление о переходе очереди RX из пустой в непустую |
| 3 | TX_DONE | Слот освобождён; status=0 OK, 1 CANCEL, 2 FAILED |
| 4 | PEER_CLOSED | Peer закрыл канал |
| 5 | RESET | Получен сброс соединения |
| 6 | RETRY_EXHAUSTED | У собственного TCP исчерпано число попыток |
| 7 | LINK_LOST | Потеря связи/перезапуск ESP |
| 8 | CONFIG_EXPIRED | Конфигурация истекла |
| 9 | CLOSED | Последнее событие закрываемого канала |
| 10 | MODE_CHANGED | Смена фактического режима обслуживания; причина в detail |
| 11 | STREAM_ERROR | В том числе UART overrun или потеря границы парсера |
| 12 | TIMEOUT | Срок OPEN, зависшего TX или CLOSE исчерпан; стадия в detail |

Для TIMEOUT значения detail равны 1 для OPEN, 2 для TX, 3 для CLOSE.
Собственный TCP преобразует подтверждённый RST в RESET и FIN в PEER_CLOSED.
Если ESP сообщает только CLOSED без уточнения причины, выдать PEER_CLOSED,
затем CLOSED. Известные WIFI DISCONNECT или перезапуск дают LINK_LOST.
При локально начатом CLOSE подтверждение закрытия самим модулем заканчивает
локальный CLOSE. RESET проверяется только на транспорте, различающем RST.

При каждом переходе пусто → непусто потребителю должно быть доступно
уведомление RX_READY. Его можно объединить с ещё не снятым RX_READY. Если
очередь событий полна, сохранить pending и опубликовать его при освобождении
места, пока данные ожидают чтения. Публикация RX, снятие уведомления и
освобождение последнего RX согласованы так, чтобы новый переход снова разрешал
уведомление. Приложение читает RX_PEEK и RX_RELEASE до EMPTY. Уже поставленное
уведомление может прийти после осушения RX, тогда RX_PEEK вернёт EMPTY.

При штатном закрытии и терминальной ошибке уже принятый корректный RX
публикуется до CLOSED; CLOSED не публикуется до освобождения этих RX и
публикации исходов всех TX. Приложение продолжает читать очередь даже после
уведомления о причине. Ошибка не превращает частично испорченный UART-блок
в валидный RX. Повторное OPEN разрешается после получения CLOSED.

ABORT — явное исключение из сохранения RX: отбрасывает ожидающий RX, прекращает
работу канала; все ещё незавершённые TX получают по одному TX_DONE/CANCEL,
включая резервацию без commit (slot известен, tag=0xFFFF). Затем CLOSED.
Повторный ABORT не создаёт новых исходов. Полная очередь событий удерживает
неопубликованный результат; слот нельзя использовать заново до публикации.
Уже опубликованный TX_DONE не заменяется CANCEL. Таймеры, возврат из ISR и
освобождение ISA не должны ждать, пока приложение прочитает события.

**CONFIG_EXPIRED:** срок проверяет первый STEP, достигший дедлайна по now_ms;
признак срока отдельный, нулевое абсолютное значение возможно при wrap.
Событие один раз на конфигурацию; новые OPEN и TX отвергаются. Активный канал
переходит к завершению, незавершённые TX отменяются, корректный RX остаётся
доступен до CLOSED. Ядро не продлевает аренду через DSS и не отправляет новые
данные с просроченными адресами. При отсутствии канала CLOSED не синтезируется.
Для следующего OPEN требуется новая INIT_CONFIG после закрытия и осушения
очередей и успешного SHUTDOWN. Конфигурация без срока обозначается явным флагом.

### SHUTDOWN

Идемпотентный экспорт основного цикла завершает работу контекста независимо
от состояния канала, в том числе после частичной инициализации или фатальной
ошибки. Первое обращение в активном контексте переводит его в STOPPING.
Шлюз маскирует маршрут PIO и прекращает новые входы STEP_ISR. OPEN и новые
TX получают STATE. Для активного канала применяются правила ABORT, включая
CANCEL на каждый незавершённый слот и CLOSED один раз. При отсутствии канала
событие CLOSED не создаётся.

Остановку выполняет ядро порциями через STEP в main, с тем же try-lock и
квотой. Оно отключает причины IRQ в карте, останавливает RX/TX, завершает
или отменяет активные операции обмена/DMA по профилю и подтверждает безопасное
состояние устройства. Шлюз продолжает выдавать квоту main и обслуживать
NEXT_EVENT. Пока остановка или выдача исходов продолжается, SHUTDOWN возвращает
WORK. После подтверждения остановки и чтения оставшихся событий SHUTDOWN
возвращает OK. Повторный вызов даёт OK без I/O и новых событий. В исходном
обнулённом контексте вызов также даёт OK без I/O.

Начало аппаратной фазы `t0` равно аргументу now_ms первого STEP, вызванного
после перехода в STOPPING. STEP фиксирует t0 до попытки захвата ISA, даже
если порция вернёт BUS_BUSY или YIELD. Приложение обеспечивает первый STEP
в пределах max_step_gap_ms после SHUTDOWN. Дедлайн наступает через
close_timeout_ms от t0 с учётом переполнения u32. Повторные STEP и SHUTDOWN
в той же попытке сохраняют t0. Задержка чтения событий после
остановки карты сама по себе не является аппаратной ошибкой. Если безопасное
состояние не подтверждено к сроку, вернуть DEVICE_FAULT, оставить маршрут
замаскированным и сохранить контекст и буферы. Каждая порция возвращает
временное отображение страниц и освобождает свой захват ISA. После устранения
причины разрешена новая попытка SHUTDOWN. Её первый STEP задаёт новый t0,
прежние события отмены повторно не публикуются. До OK память остаётся за контекстом,
а повторный INIT_CONFIG возвращает STATE. После OK шлюз восстанавливает сохранённые
PIO/IM2 и отображение страниц, затем разрешает выгрузку или повторный INIT.

## 4. Время и обнаружение отказа

В INIT_CONFIG указываются `timing_mode` (APP_COUNTER или FIXED_SCHEDULE) и
профиль квалифицированных квот. Приложение объявляет худший интервал полезного
опроса и худший интервал STEP, включая паузу. Шлюз сравнивает их с требованиями
выбранного транспорта и режима IRQ. Номер канала CTC не является полем ABI.
Владельцем часов остаётся приложение.

В APP_COUNTER адаптер приложения предоставляет шлюзу метку, частоту,
модуль счётчика и верхнюю стоимость чтения. Он сохраняет состояние IFF и
доступен во всех разрешённых точках вызова. В FIXED_SCHEDULE достаточно
номера кадровой эпохи и проверенного расписания с верхними оценками порций.
Оба режима используют тот же STEP(now_ms, budget_us) и STEP_ISR(source, budget_us).
Ядро не устанавливает таймер или обработчик часов и не вызывает код приложения
из ISR. GET_INFO описывает совместимые режимы профиля, GET_STATS возвращает
активный режим и признаки доступности измеренных максимумов. Проверка внешней
трассой обязательна и при отсутствии точной шкалы во время игры.

Для Worms `max_step_gap_ms=20`: только STEP(now_ms) двигает протокольные часы,
ARP, сроки конфигурации, закрытия и повторов. Непрерывные вызовы STEP_ISR этого
не делают. GET_INFO отдельно сообщает интервалы/возможности из §4–5 ТЗ,
эффективные лимиты буферов, время чтения часов и стеки. Возможность IRQ на
квалифицированном маршруте — в GET_INFO; результат пробы и фактический режим
данного сеанса — в GET_STATS.

GET_STATS возвращает `max_observed_step_gap_ms` по разностям now_ms между
последовательными STEP, которые проверили и продвинули протокольные сроки.
Проверка сроков в простое учитывается. Один лишь вход, отказ по бюджету или
занятая ISA без проверки сроков новую точку отсчёта не создают. Первый
результативный STEP задаёт начало, со второго максимум доступен. Пауза игры
и переполнение u32 учитываются как в остальной работе протокольных часов.

| INIT_CONFIG, миллисекунды | Профиль v1 и поведение |
|---|---|
| connect_timeout_ms | 5000 от OPEN; отсутствие ответа завершает OPEN событием TIMEOUT |
| retry_wait_ms[], retry_count | Для собственного TCP: [500, 1000, 2000, 2000, 2000], четыре повтора после первой отправки; последний интервал — ожидание перед отказом |
| send_stall_timeout_ms | 7500 без продвижения активного TX; нулевое окно, persist и лишние дубли ACK не обновляют дедлайн |
| close_timeout_ms | 2000 от CLOSE; оставшиеся TX завершаются с исходом, канал закрывается |

Эти интервалы конфигурируемы. SDK валидирует длину графика (retry_count+1),
положительные интервалы, отсутствие переполнения суммы и предел <2³¹ мс.
График — относительно начала попытки/последнего действительного прогресса,
без накопления задержки обслуживания. При полном отсутствии ACK в обычном
окне: первая передача t=0, повторы на 0,5/1,5/3,5/5,5 с, RETRY_EXHAUSTED на
первом STEP в/после 7,5 с (в пределах ещё 20 мс при соблюдении контракта).
При совпадении пределов графика и TX timeout причина RETRY_EXHAUSTED; при
застое окна без retransmit — TIMEOUT. Настройки предназначены для закрытого
игрового профиля; это не универсальные таймеры Internet TCP.

При OPEN собственного TCP общий дедлайн отсчитывается от принятия OPEN.
Если адрес next-hop неизвестен, сначала разрешается ARP. С получением MAC
начинается фаза SYN. Первая отправка каждой фазы выполняется при первой
доступной порции, повторы идут по retry_wait_ms[] относительно начала этой
фазы, для ARP каждый интервал не короче 1000 мс. Обе фазы разделяют один
connect_timeout_ms. Перед очередной передачей STEP проверяет общий дедлайн.
Если график фазы исчерпан раньше, до общего дедлайна ещё можно принять ответ.
При стандартных настройках и свободной шине для заранее известного MAC SYN
планируются на 0/0,5/1,5/3,5 с. При неразрешённом MAC запросы ARP идут на
0/1/2/4 с. В обоих случаях при тишине на 5 с публикуется TIMEOUT(OPEN),
затем CLOSED. У ESP SDK контролирует общий дедлайн команды установления
соединения, внутренние SYN/ARP выполняет прошивка.

У ESP радиосвязь, ACK и сетевые повторы скрыты прошивкой. Общие сроки OPEN,
зависшего локального TX и CLOSE исполнимы на Z80, но они не являются таймерами
TCP внутри модуля. GET_INFO явно снимает возможность настройки native TCP RTO;
обязательный запрос такой возможности отклоняется до OPEN. SEND OK не доказывает,
что молчащий peer жив. В UDP также нет TCP-повторов.

Обнаружение исчезнувшего **молчащего** партнёра — функция игрового протокола
для всех транспортов. Эталон SDK/сервера: после 1 с без подтверждённого ответа
послать запрос живости с номером; при 3 с от последнего действительного ответа
признать связь потерянной и вызвать ABORT. Чужие/старые ответы не продлевают
срок. В паузе работает тот же контроль; опоздание обнаружения ≤max_step_gap_ms
при выполнении условий сервиса. Это обмен с выбранным сервером, не ICMP PING
и не доказательство состояния второго игрока за сервером.

## 5. Парсер ESP и соответствие

В пассивном TCP запрашивать CIPRECVDATA только на число байтов, помещающееся
в свободный RX. Различать уведомление +IPD о доступности и собственно ответ
команды. В ответе принимать **фактическую** длину от 0 до запрошенной, а не
ожидаемую длину. Только эти байты — двоичная нагрузка (в том числе NUL, CR/LF,
«OK», «CLOSED», «+IPD»); не искать в ней служебные строки. До/после нагрузки
обрабатывать асинхронные уведомления и финальный статус команды по грамматике
квалифицированной прошивки. Не выдавать предварительный блок до успешного
завершения ответа; при неправильной длине/синтаксисе — ограниченное
восстановление или STREAM_ERROR. Нулевой/короткий ответ не означает FIN и
не запускает цикл немедленных повторов. Продолжение возможно после любого
байта, включая заголовок и границы уведомлений.
[Espressif: пассивный приём и CIPRECVDATA](https://docs.espressif.com/projects/esp-at/en/release-v2.2.0.0_esp8266/AT_Command_Set/TCP-IP_AT_Commands.html).

Проверять общие последовательности состояний и событий на loopback и всех шести
сборках. Для причин закрытия выбирать ожидаемый результат по возможностям
транспорта из §3. SDK проверяет
размеры и смещения общих блоков при сборке. В отдельные векторы входят
истечение конфигурации возле wrap, закрытие при заполненной очереди, FIN после
последнего RX, ABORT с несколькими тегами, zero-window, потеря heartbeat,
последний слот кольца, задетый ISA-окном стек и пассивный ответ ESP,
прерываемый после каждого байта. Стенд сопоставляет байты, исход каждого
слота и время доставки события, а не только окончательное состояние CLOSED.
